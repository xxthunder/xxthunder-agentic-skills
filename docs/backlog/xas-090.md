# [XAS-090] The closed loop's GitHub checks wait for the pushed commit, and an eval covers the CI as the gate

**Status**: Open
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/scripts/host.py` (GitHub backend), `evals/` (a CI-as-gate case, the runner's environment)
**Related**: [XAS-087](xas-087.md) (the host script; this item takes what it left open)

**Summary**:
As the author, I want the loop's GitHub checks to wait for the commit it just pushed, and an eval to cover the CI as the gate, so that a GitHub CI gate never ends on the previous commit's result and a change to that path is caught before it ships.

**Description**:
`host.py checks` waits on the pushed commit for Gitea and Bitbucket (XAS-087, Scope Decisions). On GitHub it runs `gh pr checks <branch> --watch`, which reads the pull request's current head. Right after a push GitHub may not have moved that head yet, so the command can report the previous commit's result, or "no checks reported" (exit 3, a stop) before Actions has created the runs. That is how the loop behaved before XAS-087; its docstring states it.

A possible fix: before `--watch`, wait until `gh pr view <branch> --json headRefOid` equals the commit the worktree holds for the branch, and treat "no checks reported" as pending within the same deadline. That also gives `--interval` and `--timeout` a meaning on GitHub.

No eval covers the CI-as-gate path (`host.py pr` with an interim body, `host.py checks`, the fold, the second wait). A case needs a fake CI in the eval fixtures; XAS-087 kept the shared fixtures unchanged, because a change there asks the gate for every case. This item may change them and pay that run once.

The eval sandbox reads the real `HOME`, so `host.py` sees the machine's real Bitbucket profiles and tea logins (`evals/runner.py` sets only `XDG_CACHE_HOME`). Today no real login serves the test hosts; isolating `HOME` makes the cases independent of the machine.

**Acceptance Criteria**:
- [ ] On GitHub, `host.py checks` waits until the pull request's head is the commit the worktree holds for the branch, and until checks are reported, within `--timeout`
- [ ] A red check on GitHub is still exit 1; a stale result of the previous commit never decides the verdict
- [ ] An eval case covers the CI as the gate: interim pull request, a red then a green check, the fold, the wait after it
- [ ] The eval runner gives each run its own `HOME`
- [ ] The plugin's version is bumped in `plugin.json` and `marketplace.json`
