# [XAS-053] ✅ DONE - The board shows Jira issues next to backlog items

**Status**: Done (2026-11-04)
**Priority**: High
**Component**: `plugins/xxthunder-dev-skills/skills/next/SKILL.md`, `plugins/xxthunder-dev-skills/skills/backlog-ops/SKILL.md`, `evals/`, the plugin manifests
**Related**: [XAS-046](xas-046.md) (Kanban as code), [ADR-0008](../adr/0008-the-stores-agents-md-is-the-contract.md)

**Summary**:
As a developer whose teams still keep their work in Jira, I want Jira issues on my board next
to the items of my repo backlogs, so that one board shows all my work until those teams move
to a repo backlog.

**Description**:
The board (XAS-046) knows two kinds of card: an item in a repo backlog, and `<repo> #<issue>`
for a repo without a backlog, shown without status. At work, much of the author's work is a
Jira issue, and it stays in Jira until its team switches to the backlog concept. Today such
work cannot go on the board at all, or only as a card with no title and no link to Jira.

A Jira card is a snapshot, like a `<repo> #<issue>` card: `put` takes the issue's key, link
and summary as they are at that moment, and the board never reads Jira again. Its status
stays the team's business, in Jira.

Raised on 2026-10-29; design settled on 2026-11-02.

**Scope Decisions** (author, unless marked):
- **The board never writes to Jira.** A pull or a close of a Jira card moves the card on the
  board and nothing else. (2026-10-29)
- **No migration link.** When a team moves to a repo backlog, the Jira card is dropped and the
  new item gets a card of its own; the new item does not record the old key. (2026-10-29)
- **A Jira card is a snapshot.** `put` reads the issue once; `show` prints the card as
  written — no status, no priority, no contradictions — and never calls Jira. The board does
  not notice an issue that is closed or renamed in Jira; the author drops or closes the card.
  (2026-11-02)
- **The plugin ships no Jira client.** No script, no credentials, no URL, no proxy handling:
  `put` reads the issue through the Jira access the session already has, whatever tool that
  is. The skill names no Jira tool and no credential variable. (2026-11-02)
- *(agent's call)* **A Jira project is an entry in the registry the contract names**, like a
  repo: a name, the Jira base URL, the project key as the ID prefix. The address stays
  `<name> <KEY-123>`, so the logbook works unchanged.

**Design**:

*Store contract (`Board`)* — changed in zettelkasten-template, then updated into the Kasten:
a registry entry for a Jira project, the card form
`[<KEY-123>](<jira>/browse/<KEY-123>) · [<name>](<jira>/projects/<KEY>) — <summary> [· <why now>]`,
and the rule that a Jira card's title is the issue's summary at the time of `put`, shown as
written afterwards.

*`next`* — `put` on a Jira address reads the issue's summary through the session's Jira
access; no access, or no such issue → say so and stop, no card. `show` prints Jira cards as
written, like `<repo> #<issue>` cards, and fetches nothing for them. `drop` is unchanged.

*`backlog-ops`* — "pull SPLE-123" and "close SPLE-123" on a Jira address move only the card:
no item file, no status line, no commit in any repo, no call to Jira.
