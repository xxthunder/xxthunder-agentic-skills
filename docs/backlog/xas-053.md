# [XAS-053] The board shows Jira issues next to backlog items

**Status**: In Progress
**Priority**: High
**Component**: `plugins/xxthunder-dev-skills/skills/next/SKILL.md`, `plugins/xxthunder-dev-skills/skills/backlog-ops/SKILL.md`, `plugins/xxthunder-dev-skills/scripts/`, `tests/`, the plugin manifests
**Related**: [XAS-046](xas-046.md) (Kanban as code), [ADR-0008](../adr/0008-the-stores-agents-md-is-the-contract.md), [ADR-0010](../adr/0010-other-repositories-are-read-at-origin-head-never-pulled.md)

**Summary**:
As a developer whose teams still keep their work in Jira, I want Jira issues on my board next
to the items of my repo backlogs, so that one board shows all my work until those teams move
to a repo backlog.

**Description**:
The board (XAS-046) knows two kinds of card: an item in a repo backlog, and `<repo> #<issue>`
for a repo without a backlog, shown without status. At work, much of the author's work is a
Jira issue, and it stays in Jira until its team switches to the backlog concept. Today such
work cannot go on the board at all, or only as a card with no status, title or link to Jira.

The board's rule holds for Jira too: status, priority and title are read from the item each
time, never copied onto the board. For a Jira issue, "the item" is the issue in Jira, read
through Jira's REST API instead of from a file at `origin/HEAD`.

Raised on 2026-10-29.

**Scope Decisions** (author, 2026-10-29, unless marked):
- **The board only shows Jira; it never writes to Jira.** A pull or a close of a Jira card
  moves the card on the board and nothing else. The issue's status in Jira stays the team's,
  changed in Jira by the team's own workflow.
- **Jira unreachable → the card is still shown**, with "status unknown" and the reason (no
  credentials, network, proxy, expired token). The board never goes blank because Jira is
  down.
- **No migration link.** When a team moves to a repo backlog, the Jira card is dropped and the
  new item gets a card of its own; the new item does not record the old key.
- *(agent's call)* **A Jira project is an entry in the registry the contract names**, like a
  repo: a name, the Jira base URL, the project key as the ID prefix. The address stays
  `<name> <KEY-123>`, so the logbook works unchanged.
- *(agent's call)* **Jira's status category decides the contradictions**, not the status
  name: names are custom per project, the category (`To Do`, `In Progress`, `Done`) is not.
  A card in the in-progress column whose issue is not in category `In Progress`, and a card
  whose issue is in category `Done`, are reported like their backlog counterparts.
- *(agent's call)* **The skills ship no Jira URL and no credentials.** The contract says how a
  Jira card's link is built; the credentials come from the machine's settings, as the store
  variables do.
- *(agent's call, 2026-10-29)* **Jira Cloud first.** The first Jira on the board is a Cloud
  site. Cloud's REST API authenticates with the account's email and an API token as Basic
  auth, so the script reads `JIRA_EMAIL` / `JIRA_TOKEN` from the machine's settings; the base
  URL comes from the registry, not from a variable. The status category is
  `fields.status.statusCategory.key`: `new`, `indeterminate`, `done`. Jira Server/DC, with a
  bearer token, is a later item if a board ever needs it.
- *(agent's call, 2026-10-29)* **No proxy handling of its own.** The Cloud site answered
  through the machine's `HTTPS_PROXY` without anything else; the script uses the standard
  proxy variables like any other HTTP client.

**Design** (draft, to be settled in the item's design step):

*Store contract (`Board`)* — in the template the contract comes from
(zettelkasten-template), then updated into the Kasten: a registry entry for a Jira project,
the card form
`[<KEY-123>](<jira>/browse/<KEY-123>) · [<name>](<jira>/projects/<KEY>) — <summary>`, and the rule that a Jira card's title is the issue's summary.

*Reading Jira* — a script next to `backlog.py` that takes a list of keys and prints the same
tab-separated line as `backlog.py show` (ID, status, priority, title), plus the status
category, from `GET /rest/api/3/issue/<key>?fields=summary,status,priority`. It never writes.
Unreachable or unauthorised → one line per key with an empty status and the reason on stderr.

*`next`* — `show` reads Jira cards with that script; `put` checks the issue exists before it
makes the card; `drop` is unchanged.

*`backlog-ops`* — "pull SPLE-123" and "close SPLE-123" on a Jira address move only the card:
no file, no status line, no commit in any repo, no write to Jira.

**Acceptance Criteria**:
- [ ] With a Jira project in the registry, `next put <name> <KEY-123>` makes a card in the
      contract's form, with the summary read from Jira
- [ ] `next show` prints Jira cards with status and priority read fresh from Jira, and reports
      the status-category contradictions
- [ ] With Jira unreachable, `next show` still prints every Jira card, marked "status unknown"
      with the reason, and every other card as before
- [ ] `backlog-ops` pull and close on a Jira address move only the card; nothing is written to
      Jira or to any repository
- [ ] The reading script has tests against a fake Jira, including the unreachable and the
      unauthorised case
- [ ] The store contract in zettelkasten-template describes Jira cards, and the Kasten is
      updated from it the same day the plugin is released
- [ ] The plugin's version is bumped in `plugin.json` and `marketplace.json`
