# [XAS-083] The closed loop spends its token budget on reviews, not on rebuilt context

**Status**: Open
**Priority**: High
**Component**: `plugins/xxthunder-dev-skills/skills/closed-loop/`, the `Closed loop` contract in the template's `asf/AGENTS.md`, `evals/` (fingerprint, gate), `docs/adr/0014-eval-results-count-per-plugin-and-case-version.md`
**Related**: [XAS-044b](xas-044b.md) (the run it was measured on), [ADR-0016](../adr/0016-the-closed-loop-is-a-thin-conductor-over-sdd.md), [ADR-0014](../adr/0014-eval-results-count-per-plugin-and-case-version.md)

**Summary**:
As the author, I want the closed loop to spend its tokens on what buys quality (independent reviews, tests written first) and not on context it rebuilds again and again, so that one item runs through the loop within a subscription's limits.

**Description**:
The XAS-044b run hit the subscription limit twice before its second of five units was reviewed (2026-11-08/09). Nine finished subagents used about 880k tokens, 80k to 140k each; unit 2 alone took seven agents. The eval gate had not started yet.

What bought quality, and stays: the independent reviews (unit 2's review found that a repository without `id_regex` migrated with exit 0 into a build that fails, and two behaviours no test pinned), and the split of tester and implementer.

Where the tokens went without buying quality:

1. **Rebuilt context per agent.** Every subagent reads `CLAUDE.md`, its brief, the plan's Global Constraints with both rubrics verbatim (145 lines), the reports and the diff before it starts. The contract hands both rubrics to every reviewer in full.
2. **Test additions in rounds of their own.** Because the implementer may not touch tests, every missing test is another fresh tester. In unit 2 a second fresh tester (80k) only pinned three minor behaviours the controller had asked the implementer to add without tests.
3. **Model per role.** The controller put the most capable model on a well-specified implementer task and its review.
4. **The controller's own context.** A loop started late in a long conversation re-reads that conversation on every turn.
5. **Eval re-runs.** The gate wants 3 green runs at HEAD for every case of a touched skill, plus a failing run at the base for a new or changed case; each run is a full session. A result counts for one plugin tree (ADR-0014), so any later plugin change invalidates every result.
6. **Nothing measured.** The evidence package has an optional *Measurements* section, but the loop records no token use, so no change to it can show what it saved.

**Scope Decisions**:
- **Quality stays as it is** (the agent's call, from the analysis of 2026-11-09, not decided): no review round and no tester/implementer split is dropped to save tokens; the item removes repetition and rounds that could have been bundled.

**Acceptance Criteria**:
- [ ] The loop records the tokens of every subagent and of the eval runs, and the evidence package states them under *Measurements*
- [ ] Reviewers get the rubric criteria that apply to the unit's diff, not both rubrics in full; the contract says how they are chosen
- [ ] Missing tests from one review round go to one tester dispatch; a minor finding that needs code and a test is either bundled into that round or stays deferred, never added to the implementer alone
- [ ] The skill names a model per role: a mid-tier default for testers, implementers and task reviews, the most capable one for tasks with a design decision and for the final review
- [ ] The loop starts or resumes in a fresh session when the controller's conversation is long, from the state the worktree holds
- [ ] Evals run once, after the final review and its fixes; a decision whether a result keeps counting across plugin changes outside the touched skill is recorded (ADR-0014 or a superseding ADR)
- [ ] A loop run of comparable size, measured against the XAS-044b figures, shows the saving
- [ ] The plugin version is bumped, and the template's contract change is handed on through `kasten.py export`
