# [XAS-092] The closed loop takes the ESE 2026 live-demo story DEMO-002 from the board to a green pull request

**Status**: Open
**Priority**: High
**Component**: `plugins/xxthunder-dev-skills/skills/closed-loop/`, the demo repository [xxthunder/ESE-2026-demo](https://github.com/xxthunder/ESE-2026-demo)
**Related**: [XAS-055](xas-055.md) (the closed loop), [XAS-080](xas-080.md) (scripts in the dev container), [XAS-083](xas-083.md) (token budget), [XAS-087](xas-087.md) (host script), [XAS-090](xas-090.md) (GitHub checks)

**Summary**:
As the author and co-speaker of the ESE Kongress 2026 talk "Frag doch den Agenten!", I want
to run the whole closed loop on the talk's live-demo story and judge what comes out, so that
the loop is accepted end to end on a repository it has never seen, and the live demo is
rehearsed with the same run.

**Description**:
The evals test the loop's steps one at a time. Nothing yet runs all of them in a row on a
repository that was not built for the loop. The talk's live demo is such a run: the
speakers put a user story into the loop at the start of the talk, and the agent implements
it while they talk.

**The demo repository.** [xxthunder/ESE-2026-demo](https://github.com/xxthunder/ESE-2026-demo)
holds SPLed without the Auto Off feature, as one commit without SPLed's history, so the
agent cannot find the old solution in `git log`. The branch
`feature/ese-demo-without-auto-off` in avengineers/SPLed holds the same removal on top of
SPLed's history; it is not meant to be merged. What was removed: the component
`components/auto_off`, its `KConfig` entries, its RTE interface, its calls in `spled` and
`power_signal_processing`, and its selection in the variants. What stays: the requirements
REQ_39, REQ_40 and REQ_59 and the architecture that realizes them. `AGENTS.md` uses
Brightness Adjustment as its CMake example, so it does not name the solution.

**The item.** The demo repository has its own backlog with the prefix `DEMO`. DEMO-002
"Auto Off" holds the user story of the slide `docs/ai_journey/user_story.md` in
avengineers/ESE-2026, word for word, in German. The registry `engineering/repos.md` of the
author's Kasten has the row `ESE-2026-demo | DEMO`.

**The CI.** It runs only the Linux job, so that a run ends within the talk. At the start
state it is green: 93 of 93 tests, about 2½ minutes. Without the Windows job every check
also runs locally, so the CI is a confirmation, not the gate.

**The flow on stage.** The Q&A round on the plan happens before the talk; its answers are
committed into DEMO-002 as Scope Decisions. At the start of the talk the speakers say
"Energie!". The implementation runs while they talk. The CI of the pull request runs at the
end. The goal is variant reports worth showing after 20 minutes.

**What this run tests that no eval does:**
- The item is found through the registry, in a repository the session did not start in.
- The repository has no `Closed loop` section, so the gate is derived. It has a
  `pypeline.yaml`, which comes before the workflows in the contract's list, so the derived
  gate is `pypeline run`, not the commands of `ci.yml`. Whether that is the right gate is
  part of the judgment.
- The repository has a dev container, so its commands and its worktree belong in there
  ([XAS-080](xas-080.md)).
- The pull request and its checks go through the host script on GitHub
  ([XAS-087](xas-087.md), [XAS-090](xas-090.md)).

One run answers two questions, judged apart: does the contract hold (the UAT), and does the
run work on stage (the rehearsal).

**Acceptance Criteria**:
- [ ] The demo repository's start state carries the tag `demo-start`.
- [ ] A reset puts the demo repository back to `demo-start` between runs: `develop`, open
      pull requests, branches and the board card. It is written down as exact commands in
      this item.
- [ ] Each run's measurements are recorded in this item: time from "Energie!" to the first
      variant report, to the gate green, to the pull request, and to its CI green; the
      number of review rounds; the number of times the author had to step in; the cost in
      tokens.
- [ ] Each finding of a run that the loop or the contract must fix is a backlog item of its
      own, linked here.

**UAT**:
- [ ] "Nimm DEMO-002 in die Loop" in a session started in another repository finds DEMO-002
      through the registry, the checkout at `~/dev/xxthunder/ESE-2026-demo`, and its rules.
- [ ] The Q&A answers stand in DEMO-002 as Scope Decisions on `develop` before the plan is
      written.
- [ ] After "Energie!", the loop reaches the pull request without input from the author.
- [ ] The gate runs in the demo repository's dev container, builds every variant and runs
      the selftests. The evidence package names it, where it came from and where it ran.
- [ ] The evidence package has every section of the contract, in the contract's order.
- [ ] The author judges each of DEMO-002's five acceptance criteria as met, from the diff and
      the reports.
- [ ] The CI of the pull request is green.
- [ ] A variant report with the Auto Off component is worth showing 20 minutes after
      "Energie!".

**Open Questions**:
- How many runs in a row from `demo-start` must pass before the author goes on stage with
  it?
- Is `pypeline run` the right gate for SPLed, or does the registry need a gate correction?
