# [XAS-094] The closed loop's GitHub checks never read an empty check list as green, and name the checks they read

**Status**: Open
**Priority**: High
**Component**: `plugins/xxthunder-dev-skills/scripts/host.py` (GitHub backend, `checks`), `tests/`
**Related**: [XAS-090](xas-090.md) (waits for the pushed commit; this item takes the verdict on an empty list and the check names), [XAS-087](xas-087.md) (the host script)

**Summary**:
As the author, I want `host.py checks` on GitHub to answer green only when at least one check ran and every one passed, and to list the checks it read, so that a loop whose CI is the gate never ends without a CI result, and the evidence package names the checks that decided it.

**Description**:
Found in the loop for CmdPal.Extension.Shortcuts CPS-006 on 2026-11-13 (pull request #8, gh 2.103.3). Right after `host.py pr` opened the pull request, `host.py checks` answered `{"state": "green", "checks": []}` with exit 0, before GitHub Actions had created a run. Run 43520996068 started some seconds later. Six more calls over two minutes gave the same answer. After the fold and the force push, the first call again answered green, this time before run 43521671017 on the folded commit had finished. The loop would have ended on a green gate that no CI produced. The session read the real verdict with `gh pr view 8 --json statusCheckRollup` and `gh run list` instead.

Two defects in the GitHub backend:

1. **The verdict.** `checks` returns green whenever `gh pr checks <branch> --watch` exits 0. The docstring and XAS-090 expect "no checks reported" to exit non-zero (exit 3, a stop), but in this run gh exited 0 with no checks reported. An empty set of checks is not a green gate.
2. **The list.** `checks` always returns `"checks": []` on GitHub, also when checks ran. The other backends return `[{"name", "state"}]`. The skill's *Gate* section asks for the CI's checks and their results, so the package has to read them from somewhere else.

A possible way: read `gh pr view <branch> --json headRefOid,statusCheckRollup` (or the check runs of the head commit through `gh api`) and poll it like the Gitea and Bitbucket backends do. That gives the names and states, and `--interval` and `--timeout` apply. It overlaps XAS-090's first criterion, which waits until the head is the pushed commit; whichever item lands first does the polling, and the other one builds on it.

**Acceptance Criteria**:
- [ ] On GitHub, `host.py checks` answers green only when at least one check is reported for the commit and all of them passed; with no checks reported it keeps waiting until `--timeout` and then exits 3, with a test against a fake `gh`
- [ ] On GitHub, `checks` lists every check it read as `{"name", "state"}`, green and red alike, with a test
- [ ] The docstring states the GitHub behaviour as built
- [ ] The plugin's version is bumped in `plugin.json` and `marketplace.json`
