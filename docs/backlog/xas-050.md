# [XAS-050] Eval sessions get only the permissions the sandbox needs

**Status**: Open
**Priority**: Medium
**Component**: `evals/runner.py` (`TOOLS`, `claude_command`), `tests/evals/test_runner.py`
**Related**: [XAS-047](xas-047.md) (the evals; this question was open there when it closed)

**Summary**:
As a maintainer running the evals on my own machine, I want each headless session limited to what its sandbox needs, so that a skill that misbehaves under test cannot touch anything outside the sandbox.

**Description**:
The runner starts every case with `claude -p … --allowedTools Bash Read Edit Write Glob Grep Skill`. `Bash` is unrestricted, so the session may run any command anywhere the user may. Isolation today rests on the environment: user settings are not loaded, every store variable points into the sandbox or is cleared, and the session starts in the sandbox's consumer checkout. In 84 of 84 runs for XAS-047 no session left its sandbox — but nothing enforced that.

The skills need `Bash` for real work: the plugin's `store` and `backlog.py` scripts, `git` in the sandbox repos, `uv run`. A restriction must keep those and refuse the rest.

**Scope Decisions** (author, 2026-10-27, unless marked):
- *(agent's call)* **Enforce, then measure**: a restriction is only done when all cases still pass 3 of 3 under it.
- *Open*: the mechanism — `--allowedTools` patterns such as `Bash(git:*)`, a `PreToolUse` hook that refuses paths outside the sandbox, or an OS-level sandbox for the `claude` process.
- *Open*: whether `Read`, `Edit` and `Write` are limited to the sandbox as well, and how the plugin directory stays readable.

**Acceptance Criteria**:
- [ ] A session cannot run a command or write a file outside its sandbox; a case proves it by trying
- [ ] The skills' own scripts, `git` and `uv run` keep working inside the sandbox
- [ ] Every case still passes 3 of 3 runs under the restriction
- [ ] `CONTRIBUTING.md` states what a session may do
- [ ] The runner's permission logic has unit tests under `tests/`
