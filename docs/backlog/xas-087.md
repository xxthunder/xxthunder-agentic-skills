# [XAS-087] The closed loop talks to its host through one script, with backends for GitHub, Gitea and Bitbucket Server

**Status**: In Progress
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/skills/closed-loop/SKILL.md` (package step, CI-as-gate step), a new script in `plugins/xxthunder-dev-skills/scripts/` with its tests, `evals/`
**Related**: [XAS-055](xas-055.md) (the closed loop, built GitHub-only), [XAS-067](xas-067.md) (Bitbucket Server and Jenkins, superseded by this item)

**Summary**:
As the author, I want the loop to open its pull request and wait for its checks on whatever host serves the repository, through one script with a backend per host, so that a loop on GitHub, Gitea or Bitbucket Server ends with a pull request, and a further host is one more backend instead of another change to the skill.

**Description**:
The first version of the loop opens pull requests and waits for checks on GitHub only, through `gh` (XAS-055, Scope Decisions). On any other remote it stops with "unsupported remote". The author's repositories sit on three hosts: GitHub, Gitea (the Kasten, the home lab repositories) and a Bitbucket Server with Jenkins at work. On 2026-11-09 the loop for zettelkasten ZK-041b ran green to its gate, then stopped, and the session finished the pull request by hand; on 2026-11-12 openhab-conf joined the loop with the same gap (openhab-conf OHC-017).

The skill uses `gh` in three places:
1. `gh pr create --body-file`, at the end of the package step;
2. `gh pr edit --body-file`, when the CI is the gate and the pull request was opened earlier with an interim body;
3. `gh pr checks --watch`, only where the CI is the gate.

These come down to two operations the loop needs from any host (author, 2026-11-12):
- **Open or update the pull request**, the evidence package as its body, and give its URL.
- **Wait for the pull request's checks** until they are final, the verdict as the exit code: 0 green, anything else red.

The skill calls one script for both; a backend per host does the work:

| Host | Open or update | Wait for checks |
|---|---|---|
| GitHub | `gh pr create` / `gh pr edit` | `gh pr checks --watch` |
| Gitea | `tea pr create` / `tea pr edit`, with a login whose token reaches the repository | the head's commit status from the Gitea API, until final; `tea` has no command that waits |
| Bitbucket Server | its REST API, or an installed Bitbucket Server plugin that creates pull requests | the Jenkins build status on the head commit, until final |

**Choosing the backend.** The plugin stays portable and names no host: the backend is chosen by which CLI login serves the remote's host, or by an entry in the machine's own configuration, as the board's store is. A remote no backend serves keeps the "unsupported remote" stop.

**Further hosts.** GitLab (`glab`) and Azure DevOps (`az repos`) have the same shape and would each be one more backend, without a change to the skill; none is built until a repository needs it. Gerrit reviews single changes rather than branches and does not fit the two operations.

Before building: look at what the installed plugins, `gh`, `tea` and Bitbucket tooling already do, and build only the gap.

**Acceptance Criteria**:
- [ ] The skill opens, updates and waits for its pull request only through the script's two operations; it names no host CLI itself
- [ ] On GitHub the loop behaves as before
- [ ] On a Gitea remote the loop opens or updates its pull request with the evidence package as the body, and where Gitea Actions is the CI, waits for the checks and treats a red check as a red gate
- [ ] On a Bitbucket Server remote the loop opens or updates its pull request, and where Jenkins is the CI, waits for the build and treats a red build as a red gate
- [ ] A remote no backend serves, or a backend without a login for the remote, stops the loop with "unsupported remote" and names what is missing
- [ ] No host name or URL of the author's sites is written into the plugin
- [ ] Tests cover the backend choice and each backend's two operations; an eval case covers the skill's use of the script
- [ ] The plugin's version is bumped in `plugin.json` and `marketplace.json`

**Scope Decisions**:
- **One script, a backend per host** (author, 2026-11-12), instead of one item and one skill change per host: XAS-067 is folded in, and a further host is a backend, not a skill change.
- **Three backends now**: GitHub, Gitea, Bitbucket Server with Jenkins. GitLab and Azure DevOps wait for a repository that needs them; Gerrit is out.
- **The backend is chosen by login** (author, 2026-11-12): each backend asks whether its own login serves the remote's host — `gh auth status --hostname <host>`, a `tea` login with that URL, a Bitbucket profile with that URL; the first that does is the backend. No machine configuration of its own.
- **Bitbucket Server through its REST API, called by the script itself** (author, 2026-11-12), with the token of the matching profile in `~/.bitbucket/profiles.json`. The `bb-*.py` scripts of another marketplace are not called: they cannot update a pull request or wait, and the plugin would depend on another plugin's install path.
- **Jenkins' verdict is read from Bitbucket** (author, 2026-11-12): the build statuses Jenkins reports on the head commit, until none is in progress. No Jenkins credentials.
- **Gitea as described: `tea` for the pull request, the Gitea API for the checks** (author, 2026-11-12). The backend runs where a `tea` login exists; tests use a fake `tea`. Machines without Gitea repositories need no `tea`.
- **GitHub serves a host when `gh auth token --hostname <host>` gives a token; a remote without a host goes to `gh`** (author, 2026-11-12), whose own call then decides, as before this item. This keeps the shared eval fixtures unchanged: a change there would ask the gate for every case of every skill. One new eval case shows the "unsupported remote" stop on a host no login serves.
