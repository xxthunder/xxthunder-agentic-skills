# [XAS-087] Gitea hosts the closed loop's pull request and checks

**Status**: Open
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/skills/closed-loop/SKILL.md` (package step, CI-as-gate step), `plugins/xxthunder-dev-skills/scripts/` (if waiting for checks needs a script), `evals/`
**Related**: [XAS-055](xas-055.md) (the closed loop, built without this), [XAS-067](xas-067.md) (the same for Bitbucket Server and Jenkins)

**Summary**:
As the author, I want the loop to open its pull request on Gitea and wait for its checks there, so that a loop on a repository hosted on Gitea ends with a pull request instead of the "unsupported remote" stop.

**Description**:
The first version of the loop opens pull requests and waits for checks on GitHub only, through `gh` (XAS-055, Scope Decisions). On any other remote it stops with "unsupported remote". Several of the author's repositories, the Kasten among them, sit on Gitea. On 2026-11-09 the loop for zettelkasten ZK-041b ran green to its gate, then stopped there, and the session finished the pull request by hand.

The skill uses `gh` in three places:
1. `gh pr create --body-file`, at the end of the package step;
2. `gh pr edit --body-file`, when the CI is the gate and the pull request was opened earlier with an interim body;
3. `gh pr checks --watch`, only where the CI is the gate.

For Gitea, `tea` covers the first two (`tea pr create`, `tea pr edit`, with a login whose token has access to the repository). `tea` has no command that waits for a pull request's checks; where Gitea Actions is the CI, the commit status of the head has to be read from the Gitea API until it is final.

Before building: look at what the installed plugins and `tea` already do, and build only the gap. Keep the plugin portable: the skill finds the `tea` login that serves the remote, and names no host.

**Acceptance Criteria**:
- [ ] On a Gitea remote the loop opens or updates its pull request with the evidence package as the body
- [ ] Where Gitea Actions is the CI, the loop waits for the pull request's checks and treats a red check as a red gate
- [ ] Without a `tea` login for the remote, the loop stops with "unsupported remote" and names the missing login
- [ ] The "unsupported remote" stop still holds for every other host
- [ ] No host name or URL of the author's sites is written into the skill
- [ ] An eval case or a test covers the host choice
- [ ] The plugin's version is bumped in `plugin.json` and `marketplace.json`
