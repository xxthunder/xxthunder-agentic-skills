# [XAS-032] Establish whether `retrospective` triggers in practice

**Status**: In Progress
**Priority**: Low
**Component**: `plugins/xxthunder-dev-skills/skills/retrospective/SKILL.md`

**Related**: Found reviewing all dev skills alongside [XAS-030](xas-030.md).
Unlike that item this is a question, not a defect: nothing here is duplicated
and nothing is wrong.

**Summary**:
As a maintainer, I want to know whether `retrospective` fires when it should,
so that a 228-line skill is either earning its place or knowingly kept for a
reason other than use.

**Description**:
`retrospective` is the second-largest skill in the plugin at 228 lines, behind
`commit-helper`. It duplicates nothing in `superpowers` — `receiving-code-review`
is about evaluating feedback, not about capturing an incident and updating
project guidelines. Its content is sound: five workflow steps, a root-cause
category taxonomy, two worked examples, and a file decision matrix.

The open question is whether it ever runs. Its trigger list is *"I am not
happy", "this is not what I wanted", "you shouldn't have done that", "that's
wrong", "this is incorrect"*, plus a "why did you X?" asked in a corrective
tone — with an explicit instruction not to fire on neutral curiosity.

During the long session that produced XAS-027 and its substories, the user
corrected the agent repeatedly and pointedly: an imprecise term challenged with
"BE MORE PRECISE!", a mis-scoped reference challenged with "What are you
talking about?", an unwanted artifact challenged with "This is exactly what I
wanted to avoid". Several of those are close in shape to the documented
triggers. The skill fired **zero** times.

That does not mean it is broken. Three readings fit and they lead to different
outcomes:

1. The triggers are too literal — real dissatisfaction rarely uses those exact
   phrases, and the tone condition is doing work the model cannot judge
   reliably.
2. It fired correctly by not firing — those corrections were resolved inline
   and a formal retrospective would have been ceremony.
3. It is competing with the corrections themselves: by the time the user has
   said what is wrong, fixing it is more useful than analysing why.

**Investigation** (2026-08-23), against the transcript of the session that
produced XAS-027 rather than against the skill text.

Seven corrections in that session plausibly matched a documented trigger. The
skill fired **zero** times. The strongest case is the first:

| # | What the user said | Matches |
|---|---|---|
| 1 | *"why is there a superpowers' plan document in the repo? This is exactly what I wanted to avoid."* | **two** triggers at once — a corrective "why did you X?" and a near-verbatim "this is not what I wanted" |
| 2 | *"What do you mean by 'outside the durable record'… BE MORE PRECISE!"* | the catch-all |
| 3 | *"Dude, use the default way to install uv… Tests are there to be executed."* | the catch-all |
| 4 | *"What are you talking about? What is the epic's rule?"* | the catch-all |
| 5 | *"This is not yet ready to be merged."* | the catch-all |
| 6 | *"Dude, I do not need 25000 PRs."* | the catch-all |
| 7 | *"dude, edit adr 0001, now."* | overriding a stated objection |

**Reading 1 — the triggers are too literal — is falsified.** Case 1 was nearly
verbatim and matched two triggers simultaneously. Literalness is not the
blocker; adding phrases would not help.

**Reading 3 — it competes with the correction itself — is supported, and is the
mechanism.** In every case the user wanted something fixed. Stopping to run a
five-step retrospective would have been unresponsive, and would have read as
deflection from the fix. The skill asks to interrupt at exactly the moment
responsiveness demands the opposite.

**The finding that matters most was not among the three readings.** The outcome
the skill exists to produce — a guideline updated so the mistake cannot recur —
*happened anyway, four times, without the skill*:

- Case 1 tightened the epic's plans rule, then lifted it into
  `backlog-format.md` where it ships.
- Case 2 produced a terminology pass across fourteen sites and a definition in
  ADR-0001.
- Case 4 recorded a mis-placed rule in [XAS-027k](xas-027k.md).
- The question about where TDD went added a Key Rule to `CLAUDE.md`.

Each is precisely what the skill's Step 4, *Propose Guideline Update*, is meant
to produce. They happened because the user kept pushing until the guideline
changed — not because a skill ran.

So the skill's value is not in the corrections a user drives home. It is in the
ones they make once and let go, where nobody carries the fix into a guideline.
Nothing in this session tested that case, because this user does not let go.

**Measuring instead of reading transcripts** (2026-10-21). The investigation
above counted firings by hand, in one transcript. A colleague's setup logs
every skill and agent call from a hook — one line per call, written by a
script on the tool event, nothing added to the session's context. The same
here would answer "does it fire?" with a count over every session and every
repo, and would reach the case this item could not test: the corrections a
user makes once and lets go. Shape, to be settled when this is picked up:

- A user-level `PreToolUse` hook matching the `Skill` and `Agent` tools
  appends skill or agent name, repo and timestamp to a local log file.
- It measures; it ships nothing. Hooks are Claude Code-only
  ([ADR-0004](../adr/0004-always-on-rule-is-orientation-not-enforcement.md)),
  which is fine for evidence and would not be for behaviour, so the hook lives
  in the user's settings, not in this plugin.
- Comparing the count of `retrospective` firings against the corrections in
  the same sessions still needs the transcripts; the log says where to look.

**Scope Decisions**:
- **Investigate before changing anything.** This item exists to answer a
  question. Rewriting the triggers first would be guessing.
- **Deletion is a permitted outcome.** If the honest answer is that in-line
  correction always beats a formal retrospective, that is worth knowing and
  acting on rather than keeping 228 lines out of politeness.
- **So is doing nothing.** A skill that fires rarely but valuably is fine; the
  point is to decide knowingly.

**Acceptance Criteria**:
- [x] The three readings above are tested against real transcript evidence, not
      argued from the skill text.
- [ ] A decision is recorded: keep as-is, retrigger, shrink, or remove — with
      the reasoning.
- [ ] If the triggers change, the new ones are drawn from language users
      actually used, not invented.
- [ ] If the outcome is removal, the same check as [XAS-030](xas-030.md) is
      applied first: what does this skill carry that nothing else does, and
      where does that go?

**Out of scope**:
- Rewriting the retrospective workflow itself. Its five steps are not in
  question.
- Any other skill's triggers.
