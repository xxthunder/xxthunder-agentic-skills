# [XAS-038] Make a feature branch ready to merge

**Status**: Open
**Priority**: Low
**Component**: `plugins/xxthunder-dev-skills/skills/` (new skill, if one is needed at all)

**Related**: [XAS-030](xas-030.md) (`tdd-workflow` removed as a copy of a `superpowers` skill — the reason to look before building)

**Summary**:
As the author, I want a feature branch to reach review and merge with a history
that shows the final design, checked by a reviewer who did not write it, so that
`develop` stays readable and nobody reviews their own reasoning.

**Description**:
A feature branch in `xxthunder/shortcuts` (SC-060, PR #90) had 22 commits when it
was ready for UAT. The design had changed halfway, so about ten of them rebuilt
what earlier ones had built. Others fixed the branch's own commits, ticked
acceptance criteria twice, or belonged to another item. #93 had been merged by
rebase the same day, so all 22 would have landed on `develop` one by one. The
agent rebased all 22 and resolved conflicts in intermediate commits before the
author asked whether that was really the shape to merge. The branch was then
rebuilt into 9 commits, one per logical unit, with an empty
`git diff <old-tip> HEAD`.

The rule now lives in the author's global `CLAUDE.md` ("History shows the
result"). It says to fold fixes with `git commit --fixup` and
`git rebase --autosquash`, and to reshape the branch before merge. A rule only
works when the agent remembers it at the right moment. The open question is
whether a procedure behind it is worth having:

1. Rebase onto `develop`.
2. Fold fixups, and reshape into commits that each show one logical unit in its
   final form.
3. Check that the tree is unchanged.
4. Have a reviewer with fresh context look at the result.
5. Force-push with lease after telling the author.

The author does not need this skill urgently. **Research comes first: such a
skill may already exist.**

**Research before design**:
Look for an existing skill that covers the procedure, or most of it:
- `superpowers:finishing-a-development-branch`: what it does about history,
  rebase and review today.
- `superpowers:requesting-code-review` and the built-in `/code-review`: whether
  one of them already provides the independent review.
- `commit-helper` in this plugin: whether reshaping fits there instead of in a
  new skill.
- Public skill marketplaces and plugin collections, searched for "squash",
  "clean history", "prepare PR", "branch ready".

The outcome is one of three:
- Use an existing skill as it is, and point the global rule at it.
- Extend an existing skill.
- Build a new one.

The research outcome is recorded here before any design starts.

**Scope Decisions**:
- **Rule before skill**: the rule in the global `CLAUDE.md` stays authoritative.
  A skill would only carry out the procedure; it would not restate the rule.
- **Prevention over cleanup**: fixups during the work are the primary path, and
  reshaping at the end is the case `--fixup` cannot cover (a design changed
  midway).
- **Non-interactive git**: the agent cannot run `git rebase -i`. Reshaping uses
  `--autosquash` without `-i` (git 2.44+), `reset --soft` plus staged groups,
  or `GIT_SEQUENCE_EDITOR`.
