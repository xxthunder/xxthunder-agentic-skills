# [XAS-070] The closed loop takes a backlog item, a GitHub issue or a Jira issue as its item

**Status**: In Progress
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/skills/closed-loop/SKILL.md`, `plugins/xxthunder-dev-skills/skills/backlog-ops/SKILL.md`, `plugins/xxthunder-dev-skills/scripts/board.py`, `plugins/xxthunder-dev-skills/scripts/loop.py`, `plugins/xxthunder-dev-skills/scripts/host.py`
**Related**: [XAS-055](xas-055.md) (the closed loop), [XAS-053](xas-053.md) (Jira cards on the board)

**Summary**:
As the author, I want to put any kind of item into the closed loop, a repository's backlog
item, a GitHub issue or a Jira issue, so that every repository in the registry can take
part, also one without a backlog of its own, and work tracked in a company Jira reaches a
repository through the loop.

**Description**:
The registry's `IDs` cell says which kind of item a repository has: the prefix of its
backlog, such as `XAS` or `ZKK`, or `#` when it has none and its work is an issue on its
host. A Jira issue is the third kind; its key names a Jira project, not a repository.

The skills and scripts do not agree on this. Three places each work out what an address
means, and each knows only part of it: `board.py` has its own typed parser, `closed-loop`
calls the generic `loop.py row`, and `backlog-ops` decides in prose. That is how
`loop.py row … IDs "#"` came to treat `#` as a prefix and return another repository
([XAS-070a](xas-070a.md) has the details). The loop itself takes only a backlog item: a run
for `spl-core #382` on 2026-11-05 and a run for a Jira issue on 2026-11-24 had to be helped
by hand or could not start.

The root cause is the missing single owner of the address, not the missing issue support.
So the epic builds that owner first; reading a GitHub issue and a Jira issue then become
small additions on top of it.

**Scope Decisions**:
- 2026-11-24: GitHub and Jira issues in one unit of work, rather than a second item next to
  this one. Both share the same new step, a repository named by the author instead of found
  by prefix, and splitting them would build that step twice.
- 2026-11-25: Split into an epic with three substories. The shared step becomes its own
  substory, [XAS-070a](xas-070a.md), so the GitHub and Jira substories build on it instead
  of building it twice. This keeps the reason of the 2026-11-24 decision and drops its form.
- 2026-11-25: The guard against a fourth reader of the registry is a test in the gate, not
  a rubric line. The general rubric already asks for one source of truth and did not catch
  the duplication, because no single diff showed it.

**Substories**:
- XAS-070a: One resolver turns every item address into its kind and repository
- XAS-070b: The closed loop takes a GitHub issue as its item
- XAS-070c: The closed loop takes a Jira issue as its item

**Acceptance Criteria**:
- [ ] One item of each kind, a backlog item, a GitHub issue and a Jira issue, has run
      through the closed loop to a pull request
