# [XAS-055] An item runs from the board through the superpowers loop to its repo's gate and an evidence package

**Status**: Open
**Priority**: Medium
**Component**: a skill in `xxthunder-dev-skills` that drives the loop (name to be decided), `superpowers:subagent-driven-development` (how the repo's rubric reaches its reviewer), `evals/` (cases for the loop)
**Depends on**: zettelkasten ZK-041a (the ASF contract: what a repo supplies as gate, rubric and evidence package), [XAS-058](xas-058.md) (the cost of a round)
**Related**: [ADR-0013](../adr/0013-skill-work-builds-on-superpowers-and-skill-creator.md), [XAS-049](xas-049.md) and [XAS-059](xas-059.md) (this repo's gate and rubric, the first to use the loop), HomeSmartHome HSH-099 (the second), zettelkasten ZK-041 (what replaces the PR and the code review)

**Summary**:
As the author, I want any backlog item, in any repo, to run from its card through the
`superpowers` implement–review loop until its repo's gate is green, and to end in an
evidence package, so that I confirm evidence instead of reading every diff.

**Description**:
On 2026-10-31 this item was about skill changes only. On 2026-11-01 the author widened it:
the closed loop serves every kind of development, with the Kasten as its root. The loop is
the same everywhere; what differs per repo, the repo supplies.

1. A card is pulled (`backlog-ops`); the work runs in a worktree of the target repo.
2. `subagent-driven-development` runs it: implementer, reviewer, fix rounds. This repo writes
   no orchestrator (ADR-0013).
3. The reviewer reads the diff against **the target repo's rubric**. A lead from XAS-054:
   SDD's task reviewer takes `[GLOBAL_CONSTRAINTS]` from the plan, so the rubric may enter
   through the plan.
4. The loop ends on **the target repo's gate**, never on the reviewer's approval alone. The
   gate is deterministic: tests, lint, Molecule, evals.
5. The result is an **evidence package**: what was done, which gates are green, what the
   reviewer found, what is open. For now it goes into the PR, so the loop as a whole can be
   evaluated (author, 2026-11-01).

The plugin stays portable: where a repo keeps its gate and rubric, and what the package
holds, comes from the ASF contract (zettelkasten ZK-041a), read from the target repo — never
from this plugin.

**Scope Decisions**:
- Widened from skill changes to every repo; the skill rubric moved to [XAS-059](xas-059.md).
  Decided by the author on 2026-11-01.
- The PR stays as the carrier of the evidence package for now. Decided by the author on
  2026-11-01.
- First the skills repo, then HomeSmartHome. Decided by the author on 2026-11-01.

**Open Questions**:
- Does `subagent-driven-development` take the repo's rubric through the plan's global
  constraints, or is a thin wrapper skill needed? Check this first.
- Who writes the test or eval case: the reviewer, or a step from the acceptance criteria
  before the implementer starts? The implementer should not write the test it is then
  graded on.
- The reviewer and the implementer are the same model. Which blind spots does only the gate
  or the author catch?
- The round limit: how many rounds, at the cost XAS-058 measures, before the loop stops and
  asks?

**Acceptance Criteria**:
- [ ] A skill drives the loop for an item: SDD with the target repo's rubric, ending only on
      the target repo's gate, and writing the evidence package into the PR
- [ ] It reads gate, rubric and package form from the target repo as the ASF contract sets,
      and names no repo, path or store of its own
- [ ] Eval cases: a change whose gate fails does not end the loop; a change with a green gate
      ends with a package that names the gate's result
- [ ] The plugin's version is bumped in `plugin.json` and `marketplace.json`
