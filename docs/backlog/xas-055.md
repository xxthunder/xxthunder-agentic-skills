# [XAS-055] An item runs from the board through the superpowers loop to its repo's gate and an evidence package

**Status**: In Progress
**Priority**: Medium
**Component**: a new skill `closed-loop` in `xxthunder-dev-skills`, its scripts under `plugins/xxthunder-dev-skills/scripts/` (gate and rubric lookup, test guard), `evals/` (cases for the loop)
**Depends on**: [XAS-064](xas-064.md) (a pull puts the card on the board even when the item is already In Progress), zettelkasten ZK-041a (the ASF contract: what a repo supplies as gate, rubric and evidence package), zettelkasten ZK-055 (the gate is named by a repo or derived from its CI), [XAS-058](xas-058.md) (the cost of a round)
**Related**: [ADR-0013](../adr/0013-skill-work-builds-on-superpowers-and-skill-creator.md), [XAS-049](xas-049.md) and [XAS-059](xas-059.md) (this repo's gate and rubric, the first to use the loop), HomeSmartHome HSH-099 (the second), zettelkasten ZK-041 (what replaces the PR and the code review)

**Summary**:
As the author, I want to say "put XAS-055 in the loop" and have the item pulled, planned
with me if I want, built test-first by separate agents, checked by its repo's gate, and
handed back as a pull request whose body is the evidence package, so that I confirm
evidence instead of reading every diff, and can walk away while it runs.

**Description**:
On 2026-10-31 this item was about skill changes only. On 2026-11-01 the author widened it:
the closed loop serves every kind of development, with the Kasten as its root. The loop is
the same everywhere; what differs per repo, the repo supplies. On 2026-11-04 the author and
the agent designed the skill that drives it. That design follows.

*Why.* The author starts the loop and then is often elsewhere: in another session, away, or
watching from the mobile app. So the loop asks its questions at the start, runs on its own
after that, and stops only for what only the author can decide.

*What exists and what is missing.* `superpowers:subagent-driven-development` (SDD, 7.0.0)
already runs a plan task by task: implementer, task reviewer, fix rounds, a final reviewer,
and a list of the rulings it made on the author's behalf. Its task reviewer gets the plan's
`## Global Constraints` verbatim as `[GLOBAL_CONSTRAINTS]`, and the final reviewer reads the
plan file. So the rubric reaches every reviewer through the plan, and no wrapper around SDD
is needed for that. What SDD does not do: find the target repo's gate, end on it, keep the
tests away from the implementer, and write the evidence package. SDD ends when the final
review is clean and allows no second fix wave. `closed-loop` adds exactly these parts and
writes no orchestrator of its own (ADR-0013).

*The run.* `closed-loop` takes one item and does this, in order:

1. **Find the item and its repo, then pull.** The sentence can come from any session. The
   ID's prefix names the repo: the current repo's backlog when the prefix is its own, else
   the board's registry, which also gives the local checkout. The loop reads that repo's
   rules (`AGENTS.md` / `CLAUDE.md`) and runs every later step there. It hands "pull <ID>"
   to `backlog-ops` in that checkout: the status goes to In Progress, the card goes into the
   board's in-progress column. It relies on XAS-064 for an item that is already In
   Progress.
2. **Read the contract.** It resolves the board's store and reads its `Closed loop` section
   with the plugin's `store contract`, as `backlog-ops` reads the `Board` section. Gate,
   rubric, package sections and where the gate runs come from there and from the target
   repo — never from the skill.
3. **Find gate and rubric.** A script prints the gate command, how it was found and where it
   runs, and the rubric files, for a given repo. The lookup runs fresh at every start.
4. **Ask once: "Q&A round on the plan first?"** On yes, the agent and the author talk the
   item through. Every answer goes into the item's Scope Decisions and is committed before
   the plan is written, so the plan argues from the item, not from a chat. On no, it goes
   on. This is the last planned stop with the author in it.
5. **Worktree.** The work runs on a feature branch in a worktree of the target repo, as the
   target repo's rules say.
6. **Plan.** `superpowers:writing-plans` writes the plan. Two rules on top of its own:
   - The general rubric and the repo's rubric go verbatim into `## Global Constraints`.
   - Each task with behaviour to test is split in two: `N.a` writes the failing tests,
     `N.b` makes them pass.
7. **Build test-first, with two agents.** SDD runs the plan.
   - The *tester* (task `N.a`) writes failing tests from the task and the item's acceptance
     criteria, without an implementation in sight, and shows that they fail. Its reviewer
     checks the tests against the acceptance criteria.
   - The *implementer* (task `N.b`) makes them pass and refactors. It does not change the
     tester's tests. A script checks that from the diff of `N.b`'s commits, and a change to
     one of those files sends the task back.
   - *Dispute.* When the implementer finds a test wrong, it reports `BLOCKED` with the test,
     the reason, and what it expects instead, and changes nothing. A fresh tester gets the
     dispute and either fixes the test in its own commit or rejects the dispute with a
     reason. After **two** exchanges without agreement, or when the dispute shows that an
     acceptance criterion itself is wrong, the loop stops (step 10).
8. **Gate.** After SDD's final review, the loop runs the gate where the contract says.
   - Red: one fix subagent gets the gate's output, then the gate runs again. After **two**
     red fix rounds the loop stops (step 10).
   - Where the CI is the gate, the loop pushes the branch, opens the pull request and waits
     for its checks; a red check counts as a red gate.
   - The loop never ends on a reviewer's approval alone.
9. **Evidence package.** On a green gate the loop opens the pull request (or fills the one
   step 8 opened). Its body holds the contract's sections: Item, What changes, Gate, Review,
   Measurements, Your steps, Open. *Review* lists each round's findings and how each was
   resolved, every dispute, and every ruling SDD made on the author's behalf. The loop does
   not merge and does not tick acceptance criteria; the author does both.
10. **Stop, wait, notify.** At each stop the loop sends a push notification that names the
    decision, waits for the author's answer, and continues from where it stopped. The stops
    are: the gate still red after two fix rounds, a dispute still open after two exchanges,
    an acceptance criterion found wrong, and a plan step the item does not settle.

The session's task list shows each step, so the author can follow the run from the mobile
app. A push notification also marks the milestones: plan written, gate green or red, pull
request opened with its link.

*Goals.* One sentence starts the whole run. The loop ends on a deterministic gate. The
implementer never grades its own tests. The author is asked only at the start and at a
real decision.

*Non-goals.* No orchestrator next to SDD. No merge. No ticking of acceptance criteria, no
close of the item. No ranking of the board.

*Anti-goals* — the change fails, even if it runs, if: the loop ends on a reviewer's
approval; the implementer changes a test it is graded on and nobody notices; the loop
settles a scope question alone instead of stopping; or the skill names a repo, a path or a
store of its own.

*Left to the builder.* The scripts' names and interfaces, the wording of the dispute report,
how the loop resumes after a stop, and how eval cases cut the loop into pieces small enough
to run.

The plugin stays portable: where a repo keeps its gate and rubric, and what the package
holds, comes from the ASF contract (zettelkasten ZK-041a), read from the target repo — never
from this plugin.

**Scope Decisions**:
- Widened from skill changes to every repo; the skill rubric moved to [XAS-059](xas-059.md).
  Decided by the author on 2026-11-01.
- The PR stays as the carrier of the evidence package for now. Decided by the author on
  2026-11-01.
- First the skills repo, then HomeSmartHome. Decided by the author on 2026-11-01.
- The contract is settled (zettelkasten ZK-041a, ADR-0023, 2026-11-01): the gate is the
  target repository's `scripts/gate`, exit 0 means green; the rubric is `docs/rubric.md`; a
  repository without `scripts/gate` does not take part, and the skill says so. The evidence
  package has the sections Item, What changes, Gate, Review, Measurements, Your steps, Open.
  Its gate point is superseded by the next decision.
- `scripts/gate` is optional (zettelkasten ZK-055, ADR-0026, 2026-11-03): the skill takes
  the gate the repository names — its `Closed loop` section or `scripts/gate` —, else a
  correction in the Kasten's registry, else it derives the gate from the repository's CI —
  `pypeline.yaml`, GitHub or Gitea workflows, a `Jenkinsfile`. The derivation runs fresh at
  every start and is not stored. Where the CI cannot run locally, the CI is the gate and the
  loop ends on green pull-request checks. The rubric falls back to `CONTRIBUTING.md`. Only a
  repository with neither CI nor gate does not take part. The order and the CI files are
  read from the contract, not written into the skill. Decided by the author on 2026-11-03.
- A thin conductor skill drives the loop; SDD stays as it is, and the rubric reaches its
  reviewers through the plan's Global Constraints. Decided by the author on 2026-11-04.
- The trigger is "put <ID> in the loop": pull, board, loop in one. The skill offers a Q&A
  round on the plan at the start. Decided by the author on 2026-11-04.
- At a decision only the author can make, the loop stops, waits and notifies; it does not
  open the pull request with the problem under Open. Decided by the author on 2026-11-04.
- A TDD loop inside the closed loop: a tester writes the failing tests, an implementer makes
  them pass, per plan task — the roles are split, not swapped as in human ping-pong, because
  each hand-off costs a fresh context. A wrong test goes back to the tester as a dispute,
  two exchanges at most, then to the author. Decided by the author on 2026-11-04.
- Round limits for the start: two red-gate fix rounds, two dispute exchanges. XAS-058's
  cost figures may change them. Decided by the author on 2026-11-04.
- "Put X in the loop" works from any session: the loop finds X and its repo from the
  current backlog or the board's registry. Decided by the author on 2026-11-04.
- The triggers, decided by the author on 2026-11-04 in the Q&A round:
  - *Start an item* — pull, Q&A offer, run: "put XAS-055 in the loop", "start the loop for
    XAS-055"; German "nimm XAS-055 in die Loop", "bring XAS-055 in die Loop", "starte die
    Loop für XAS-055".
  - *Go* — for the item in focus, usually right after the Q&A round; with no item in focus
    the loop asks which one and does not guess from the board: "Make it so!", "Engage!",
    "Start the loop!"; German "Energie!", "Starte die Loop!".
  - Both in one sentence skip the Q&A: "Put XAS-055 in the loop. Make it so!"
  - The skill's texts say "die Loop" (the author's choice, as in *die Schleife*); its
    `description` also covers "den Loop", because people say both.
- No eval runs the whole loop. Each case starts from a prepared state and checks one step:
  stop on a red gate, no pull request without a green gate, stop on an open dispute, no
  test change by the implementer. A whole run costs many times a normal eval run, three
  times per case, and its outcome is too noisy to tell where it failed. The whole loop is
  tested once by its first real use, on XAS-064; that run's cost goes into the pull
  request's Measurements and gives XAS-058 a real figure. Decided by the author on
  2026-11-04 in the Q&A round.
- The agent's calls on 2026-11-04, open to the author's veto:
  - The skill is named `closed-loop`, not `loop`, because Claude Code ships a `loop` skill
    for repeating a prompt on an interval.
  - The gap in `backlog-ops` pull is its own item, XAS-064.
  - SDD's files stay untouched; `closed-loop` sets three rules for the run on top of it. A
    `BLOCKED` dispute goes to a fresh tester, not to a controller ruling. A question that
    changes scope or an acceptance criterion stops the loop. The test guard runs after each
    implementer task, before its review. Every other ambiguity SDD rules on as usual, and
    its rulings are listed under Review.
  - The gate's lookup order lives only in the contract. The agent reads the order there;
    scripts do the mechanical lookups it names (a repo's `Closed loop` section,
    `scripts/gate`, a registry correction, which CI files exist). Turning CI steps into
    local commands takes judgment and is an agent step; the package names the CI file the
    gate came from.
  - Notifications use the harness's own push-notification tool where there is one; the
    skill names no outside service.
  - Tester and implementer commits are folded into one commit per unit before the pull
    request opens, after the test guard has run, so code and its tests land together.
  - The first version opens pull requests and waits for checks on GitHub only. Bitbucket
    Server with Jenkins gets a follow-up item.
  - Where a gate checks eval results instead of running evals (this repo's), the plan runs
    them: the tester at the base, where the new case must fail, and once after the change.

**Open Questions**:
- The reviewer and the implementer are the same model. Which blind spots does only the gate
  or the author catch?
- Does the reviewer set severities consistently? For now each rubric criterion names the
  severity of its findings in prose (XAS-059). Record every finding with its criterion and
  severity in the evidence package; after 10 to 20 loops, check whether the same kind of
  finding gets different severities, and whether a criterion never finds anything. Only
  then decide on more: one file per dimension with graded levels and a machine-readable
  rule, the reviewer's findings as JSON, and a script that applies the rule (the format of
  the Agentic Engineering workshop, Costa Salgado and Welti 2026).
- Should the reviewer get only the item's acceptance criteria, and state the behaviour it
  expects before it reads the diff? Today it reads the whole item.

**Acceptance Criteria**:
- [ ] "Put <ID> in the loop" pulls the item through `backlog-ops`, offers the Q&A round, and
      runs plan, SDD, gate and pull request without a further question when nothing needs
      the author
- [ ] The plan carries both rubrics verbatim in its Global Constraints and splits each task
      with behaviour to test into a tester task and an implementer task
- [ ] A script finds the gate and the rubric of a repo in the contract's order and says how
      it found them; tests cover a named gate, a registry correction, `pypeline.yaml`, a repo
      with only a GitHub workflow, and a repo with neither CI nor gate
- [ ] A script rejects an implementer commit that changes a tester's test; tests cover it
- [ ] The skill reads gate, rubric and package form as the ASF contract sets, and names no
      repo, path or store of its own
- [ ] Eval cases, each from a prepared state: a red gate after two fix rounds stops the
      loop with a notification and no pull request; a green gate ends with a pull request whose package names the gate's
      command, how it was found and its result; an open dispute after two exchanges stops
      the loop
- [ ] The skill's `description` covers the triggers in Scope Decisions, in English and
      German, with a run of `skill-creator`'s trigger tooling recorded in the pull request
- [ ] The plugin's version is bumped in `plugin.json` and `marketplace.json`
