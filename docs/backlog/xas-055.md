# [XAS-055] A skill change is reviewed against a skill rubric inside the superpowers loop, and the eval gate ends the loop

**Status**: Open
**Priority**: Medium
**Component**: the plugin's review rubric (new reference, place to be decided),
`superpowers:subagent-driven-development` (how a rubric is passed in), `evals/` (cases for the reviewer)
**Depends on**: [XAS-054](xas-054.md) (the ADR on what we adopt), [XAS-049](xas-049.md)
(the eval gate)
**Related**: zettelkasten ZK-041 (what replaces the PR and the code review)

**Summary**:
As the maintainer, I want a skill change to run through the superpowers implement–review
loop with a reviewer that knows a rubric for skills, and to finish only when that skill's
evals are green, so that I confirm evidence instead of reading every `SKILL.md` diff.

**Description**:
`subagent-driven-development` already has an implementer, a task reviewer and fix rounds.
Two things are missing for skills:

1. **A hard stop criterion.** Today the loop ends when the reviewer is satisfied, which is a
   model's judgment. For a skill, the loop is done when that skill's eval cases pass 3/3 and
   the new cases fail on `develop`. This is the RED/GREEN of `writing-skills`, checked by
   the XAS-049 guard, not by the reviewer.
2. **A rubric for skills.** The generic quality reviewer does not know what makes a skill
   good. Rubric criteria, each answered with evidence from the diff:
   - **Script before prose**: every mechanical step the skill asks for has a script that
     does it, and the skill calls the script. Examples are allocating an ID, editing a
     table of contents, computing a date, or moving a board card. XAS-051 and XAS-052 were
     findings of this kind, made by hand.
   - **Trigger**: the `description` covers the phrasings real users use, in more than one
     language where users write more than one.
   - **Portable**: no repository-specific paths or names.
   - **Phrased positively**: rules say what to do.
   - **A case per behaviour change**, written before the skill change. Whether it ran is
     the gate's job; the rubric only checks that it exists and asserts the behaviour,
     not a side effect.

What the rubric excludes: anything the gate or a test checks mechanically (XAS-054: the
reviewer does not grade eval runs).

**Open Questions**:
- Does `subagent-driven-development` take an extra rubric from outside, or is a thin
  wrapper skill needed? Check this first.
- Who writes the eval case: the reviewer, or a step from the acceptance criteria before
  the implementer starts? The implementer should not write the test it is then graded on.
- The reviewer and the implementer are the same model. Which blind spots does only the
  eval or the author catch, and does the author stay the last gate at the merge?
- Where do findings go? The default is the backlog item, never a GitHub issue.
- The round limit with evals: how many rounds, at dozens of agent sessions each, before the
  loop stops and asks?

**Acceptance Criteria**:
- [ ] The skill rubric is a file in the plugin, and the task reviewer of
      `subagent-driven-development` uses it for a change to a `SKILL.md`
- [ ] The loop for a skill change ends only on a green eval gate (XAS-049) for the touched
      skills, not on the reviewer's approval alone
- [ ] Eval cases with seeded faults: a `SKILL.md` diff that has the agent allocate an ID by
      hand is flagged under "script before prose", and a clean diff is not flagged
- [ ] The plugin's version is bumped in `plugin.json` and `marketplace.json`
