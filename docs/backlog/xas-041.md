# [XAS-041] `backlog-ops` pull: In Progress lands on the default branch at once

**Status**: In Progress
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/skills/backlog-ops/SKILL.md`,
`plugins/xxthunder-dev-skills/skills/commit-helper/SKILL.md` (if the hand-off
needs a subject it does not have),
`plugins/xxthunder-dev-skills/.claude-plugin/plugin.json`,
`.claude-plugin/marketplace.json`, `docs/architecture.md`
**Related**: [XAS-040](xas-040.md) (`next` reads items at `origin/HEAD`),
ADR-0010 (other repositories are read at `origin/HEAD`, never pulled)

**Summary**:
As a maintainer running several sessions across repos, I want a pulled item to
read *In Progress* on the default branch the moment it is pulled, so that other
sessions and `next` see who is working on what — while *Done* still lands with
the code it claims.

**Description**:
`next` reads every backlog at `origin/HEAD`
(ADR-0010, arriving with XAS-040).
A status change that lives only on a feature branch is invisible there until
the merge. In the end-to-end run of [XAS-040](xas-040.md), XAS-040 itself read
*Open* on `develop` while it was being worked on, because the pull sat on the
feature branch.

The two status changes claim different things:

- **In Progress** says *someone is working on this*. It describes the work,
  not the content of the default branch, and nothing is wrong if it lands
  before the code. Sessions and `next` need it at once — a session that cannot
  see it may pick up the same item.
- **Done**, and every ticked criterion, says *the default branch contains
  this*. Set before the merge, the default branch would claim work it does not
  have. It stays on the feature branch, in its own `docs(backlog): close <ID>`
  commit at the end of the PR, so the merge closes the item.

`backlog-ops` today stages every edit and never commits, so the pull rides in
whatever the author commits next — usually the first commit on the feature
branch.

**Scope Decisions** (author, 2026-10-21):
- **Pull goes to the default branch on its own**: before the feature branch is
  created, the pull's edit — item and README — is committed and pushed to the
  default branch, alone.
- **`backlog-ops` hands off, it does not commit.** It stays mechanics-only and
  stages; its pull ends by handing the staged edit to `commit-helper` for a
  `docs(backlog): pull <ID>` commit on the default branch, pushed. The
  never-commits rule of `backlog-ops` stands.
- **Where the default branch takes no direct push, nothing changes**: the pull
  stays on the feature branch as today. The consuming repo's own rules decide
  — its `AGENTS.md` / `CLAUDE.md`, or a refused push.
- **Done is unchanged**: the close stays the last commit on the feature branch.

**Acceptance Criteria**:
- [ ] `backlog-ops` pull ends with the hand-off: the staged pull edit, alone,
      committed by `commit-helper` on the default branch and pushed, before any
      feature branch exists
- [ ] When the repo's rules or a refused push forbid a direct push, the pull
      stays staged for the feature branch, and the skill says why
- [ ] Complete is unchanged: Done and the ticked criteria stay on the feature
      branch, as the last commit of the PR
- [ ] `docs/architecture.md` via `design-record`: the *Backlog lifecycle* key
      flow shows where pull and close land
- [ ] `plugin.json` and `marketplace.json` bumped (minor)
- [ ] Verified in a consuming repo: after a pull, `backlog.py show <ID>` on
      the `origin/HEAD` export reads *In Progress*

**Out of scope**:
- Ticking a single criterion before the close — it describes the content and
  stays with the code.
- Repositories without a backlog.
