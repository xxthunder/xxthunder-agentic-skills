**Summary**:
As a maintainer working across many repositories with a coding agent, I want
to ask on a keyword what is in progress and what comes next across all my
repositories, ranked by me in one personal list, so that I do not walk every
backlog by hand at the start of a session.

**Description**:
A colleague's setup (2026-10-21) shows the wish and its cost: a hook reports at
every session start which issues are open and in progress — but all issues live
in one central repo, away from the code they are about.

Here the items stay in their repos. What is missing is an **order across
repos**. `**Priority**` (High/Medium/Low) says how much an item matters inside
its own backlog; priorities from two backlogs cannot be compared, a rank can.

**What exists already, and why it does not cover this** (the
[XAS-030](xas-030.md) check):

- `backlog-ops` and `backlog.py` work on one repo's backlog, the one the
  session is in.
- `logbook` records what was started and finished across repos — the
  *in progress* half — but holds no intention about what comes next.
- The `SessionStart` hook says *where* the design record lives, not what is in
  it.

Nothing holds a ranked "this comes next" across repos, and nothing shows it
together with what is in progress. That is the gap.

**The direction rule** holds as for [XAS-034](xas-034.md) and
[XAS-035](xas-035.md): the list points into repositories; no repository points
into the list. What knows the list is the machine.

**The rules live in the store, not in the skill**
([ADR-0008](../adr/0008-the-stores-agents-md-is-the-contract.md)). The skill
reads the store's `AGENTS.md` and follows the section headed `Next`: where the
list is, its line format, how a repo name resolves to a remote and a local
checkout, where *in progress* is read from, the language. The skill hardcodes
only that this section exists and names those things.

**Operations**, `/next` or the natural phrases "what's next" and "was steht
an". The trigger description ties them to work across repositories, so that
everyday use of the phrases does not set off a fetch of every repo:

- **`show`** (default) — resolve the store fresh (`pull --rebase`). For every
  repo the list or the in-progress source names: `git fetch`, then read the
  item from `origin/<default>` with `git show`. Print *In progress* and *Next*,
  each entry with title, status and priority from the item itself.
  Contradictions are reported, not smoothed over: an item on the list that is
  already Done; an item In Progress in its backlog without an open start in the
  in-progress source, and the reverse; an address that resolves to no item.
- **`put`** — place an item: `put HSH-089`, `put OHC-004 after OHC-003`,
  `put SC-061 at 1`. One commit, pushed.
- **`drop`** — remove an item from the list. One commit, pushed.

**What the skill never does:** `pull`, `checkout` or otherwise touch the
working tree of any repo other than the store; write into a consuming repo;
change an item's status or priority; run without configuration; mention any
specific store in its own text.

**Scope Decisions** (2026-10-21):
- **A skill on a keyword, not a hook at every session start.** A hook costs
  context in every session, whether the answer is wanted or not, and is Claude
  Code-only ([ADR-0004](../adr/0004-always-on-rule-is-orientation-not-enforcement.md)).
- **One ranked list in the store; `**Priority**` stays in the backlogs.** The
  rank is a commitment ("this comes after that"), the priority a weight. The
  skill reads the priority and never writes it.
- **Always fresh, never pulled.** `git fetch` on every repo involved, then read
  from `origin/<default>`. A `pull` in a checkout would disturb a session
  working there at the same time. Only the store is pulled, because the list is
  written there.
- **Reuse, do not add.** The store resolver and commit-and-push from
  [XAS-034](xas-034.md); item parsing — status, priority, title — from
  `backlog.py`, because the item format is this plugin's own
  (`references/backlog-format.md`). The list format belongs to the store and is
  handled in prose, as `logbook` handles the log.
- **Fresh items through a temporary directory.** `backlog.py` reads a
  directory, and after a fetch the fresh items exist only at
  `origin/<default>`. The skill exports them —
  `git archive origin/<default> docs/backlog | tar -x -C <tmp>` — and runs
  `backlog.py --dir <tmp>/docs/backlog show <ID>...`. Reading from a git ref is
  added only once a second skill needs it.
- **`backlog.py` gains one read-only command, `show`** (found while
  implementing, 2026-10-21): the script parsed ID, title and status but not
  `**Priority**`, and had no command that prints an item. `show <ID>...`
  prints `ID`, status, priority and title, tab-separated — `—` for a missing
  priority, every item without IDs, unknown IDs on stderr with exit 1. This
  replaces the earlier "`backlog.py` stays unchanged".
- **`logbook done` hands off** with one line: "Drop `<address>` from the next
  list?" — the same seam as `backlog-ops` → `logbook`. `logbook` does not call
  the skill and does not know whether a list is configured.
- **The logbook's store is the list's store.** The skill resolves it with
  `LOGBOOK_PATH` and `LOGBOOK_REMOTE`; no variables of its own. The list and
  the log are read together, so a second store would only be a second thing to
  configure.
- **A repo not cloned locally: ask.** The skill names the repo and asks
  whether to clone it to where the store's contract says repos live. Yes
  clones it and goes on; no leaves it out and the report says so.
- **Minor version bump** of `xxthunder-dev-skills`: a new skill, no breaking
  change; the `logbook` line rides in the same bump.

**Acceptance Criteria**:
- [ ] `SKILL.md` describes `show`, `put` and `drop`, the resolution order, the
      `AGENTS.md` `Next` contract, the direction rule and the never-list; its
      trigger description names the operations and the natural phrases
- [ ] `show` runs `git fetch` on each repo involved and leaves every working
      tree other than the store's untouched (`git status` and `HEAD` unchanged)
- [ ] `show` reports each contradiction named in the description, each with a
      test or an end-to-end case
- [ ] Item parsing goes through `backlog.py show` on the items exported from
      `origin/HEAD`, with tests for the new command (TDD, green on both matrix
      jobs); the temporary directory is removed afterwards
- [ ] A repo that is not cloned is asked about, not skipped silently or cloned
      unasked
- [ ] Negative control: without configuration and outside a store, the skill
      stops with a message
- [ ] `grep -ri` over the skill directory finds no path, remote or name of any
      specific store
- [ ] `logbook` `done` ends with the one-line handoff
- [ ] `docs/architecture.md` via `design-record`: the skill in the components
      diagram and a *What comes next* key flow
- [ ] `plugin.json` and `marketplace.json` bumped (minor); `README.md` and
      `CLAUDE.md` skill lists updated
- [ ] Verified end to end from a consuming repo that is not the store, against
      at least three repos

**Out of scope**:
- The list's own conventions — location, line format, language. They belong to
  the store and are read from its `AGENTS.md`.
- A `SessionStart` hook that shows the list.
- Changing an item's status or priority; that stays with `backlog-ops`.
