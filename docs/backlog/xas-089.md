# [XAS-089] ✅ DONE - The implementer commits its own change of a unit with commit-impl

**Status**: Done (2026-11-23)
**Priority**: Medium
**Component**: `evals/` (a case for the closed loop)
**Related**: [XAS-055](xas-055.md) (the closed loop), [XAS-080](xas-080.md) (where the loop's scripts run), zettelkasten ZK-041b (the architecture model of the loop, whose `Unit` view follows this item)

**Summary**:
As the author, I want every role of the closed loop to commit its own change, the implementer
its first change of a unit with `loop.py commit-impl`, so that a unit always folds into one
commit under its final message, whoever writes the plan.

**Description**:
Build step 1 of `closed-loop` says what happens to the implementer's first commit of a unit:
"stage the change, write the unit's final message to a file outside the working tree, and run
`loop.py commit-impl <worktree> <B> <file>`". It does not say who does it. The skill is read by
the session, so it reads as the session's step; but the change is made by the implementer
subagent, whose `subagent-driven-development` prompt tells it to commit its work, and the Plan
section does not override that.

An implementer that commits with a plain `git commit` leaves no `amend!` of the tester's commit
`B`. The guard still works, since it compares file ranges; but `loop.py fold` has nothing to fold:
tests and code stay two commits, the unit's final message never lands, and nothing stops or
warns. In zettelkasten ZK-041b (2026-11-09) the run folded only because the plan, written by
the session, said by hand that the controller commits through `commit-impl`.

The other commits of a unit already name their committer: the tester commits its tests, a
fresh tester in a dispute and the fix subagent at the gate commit with `loop.py fixup`. Only
this one is open.

The fix (the author's choice, 2026-11-11): the implementer commits it. The `N.b` task hands it
the full SHA of `B`; it stages its change, writes the unit's final message to a file outside
the working tree, and runs `loop.py commit-impl` itself; its later commits of the unit go
through `loop.py fixup`, as now. The session commits nothing of a unit. The other option,
the session commits and the plan tells the implementer to stage only, was dropped: it keeps a
handover the implementer does not need.

**Scope Decisions**:
- 2026-11-18: the eval case resumes the loop at `step=build`, on a prepared one-unit plan
  whose `N.b` task says nothing about who commits, with the tester's commit `B` and `tests_1`
  already in the state. It checks the implementer's commit and the fold. A case that resumes
  at `step=plan` and only reads the written plan was dropped: it shows neither the commit nor
  the fold, which are the claim of this item.
- 2026-11-18: XAS-089 starts after XAS-080 is merged, and branches from that `develop`. Both
  change `closed-loop/SKILL.md` and the plugin version; one after the other avoids a rebase
  of a running loop.
- 2026-11-19: the prepared plan's `1.b` task ends with an explicit `git commit -m ...` step,
  as `superpowers:writing-plans` writes every task by default; this replaces "says nothing
  about who commits" in the first decision. A plan that names no committer passed 3 of 3 runs
  against the base: the eval session did the unit itself, without a subagent, and followed
  the skill's `commit-impl` line, so it never met the defect. A plan with a plain commit step
  is the realistic trigger, and the skill must override it. Allowing the Agent tool in the
  eval runner was not chosen: it changes the shared fingerprint, so every case of every skill
  would need a fresh 3 of 3, and nothing makes a `claude -p` run invoke
  `subagent-driven-development` reliably.
- 2026-11-20: the item ships the eval case as a regression guard, with no change to
  `closed-loop/SKILL.md` and no version bump. The defect does not reproduce on today's
  `develop`: with the plain `git commit` step the case passed 3 of 3 runs at the base, and
  the third run's transcript shows the session dispatch an implementer subagent, rule on its
  own that `1.b` commits through `loop.py commit-impl`, and the implementer run it. Six base
  runs gave no failure, so the first criterion cannot hold, and a skill change would fix
  nothing a run can show. The case stays to pin the behaviour. Superseding the item without
  the case was not chosen: it is cheaper now, but nothing would catch a regression.
