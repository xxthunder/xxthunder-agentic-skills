# [XAS-046] Kanban as code: `next` shows a board, `backlog-ops` moves its cards

**Status**: Open
**Priority**: High
**Component**: `plugins/xxthunder-dev-skills/skills/next/SKILL.md`, `plugins/xxthunder-dev-skills/skills/backlog-ops/SKILL.md`, `plugins/xxthunder-dev-skills/skills/logbook/SKILL.md`, `docs/architecture.md`, the plugin manifests
**Related**: [XAS-040](xas-040.md) (`next` as a ranked list), [XAS-041](xas-041.md) (pull lands on the default branch), [ADR-0007](../adr/0007-cross-repo-stores-are-configured-not-discovered.md), [ADR-0008](../adr/0008-the-stores-agents-md-is-the-contract.md), [ADR-0010](../adr/0010-other-repositories-are-read-at-origin-head-never-pulled.md); the store side is zettelkasten ZK-049b

**Summary**:
As a developer working with agents, I want what comes next and what I am working on as a Kanban board in one Markdown file, kept up to date by the skills that pull and close items, so that I keep the overview without JIRA and can look at the board on Gitea or GitHub as it is.

**Description**:
`/next` prints two blocks — *In progress* from the logbook's open starts, *Next* from a ranked list — plus contradictions. The author finds the output hard to scan (2026-10-27). A board with columns reads at a glance. The idea came up with a colleague: work Kanban-as-code instead of in JIRA, the board in a repo next to everything else.

Today the list is coupled to the logbook in two ways: `next` finds its store through `LOGBOOK_PATH`/`LOGBOOK_REMOTE`, and *in progress* is read from the log. The logbook is optional — not everyone who wants a board wants a chronicle. And the list changes only by hand: `logbook done` suggests a `drop`, nothing puts a pulled item into progress.

This item makes the list a board with two columns, decouples it from the logbook entirely, and has `backlog-ops` move a card on pull and close when a board is configured. The board's format, path and language stay the store's ([ADR-0008](../adr/0008-the-stores-agents-md-is-the-contract.md)), in a contract section headed `Board`; the store side — contract, the file, the setup — is zettelkasten ZK-049b.

**Scope Decisions** (author, 2026-10-27, unless marked):
- **Kanban only, two columns: Next | In Progress.** No Done column: a close takes the card off the board. A Scrum mode — a Done column, emptied at a review event — is a later item.
- **The board is a Markdown table in one file** that renders on Gitea, GitHub and in Obsidian as it is. The two columns are independent lists; a row pairs nothing. The order of *Next* is the rank.
- **A card is a link to the item, its title, and the author's optional reason.** The title is copied into the card on purpose, so the board reads on the forge without a skill — this reverses the "never copy the title" rule of XAS-040. Status and priority stay out of the card.
- **A pull puts the card into In Progress — in every repository, whether or not the card was on *Next* before.** A close takes it off the board. `backlog-ops` does both, and only when a board is configured; without one it behaves exactly as today.
- **`next` knows nothing of the logbook.** It finds its store through its own variable pair, `BOARD_PATH`/`BOARD_REMOTE`, and reads *in progress* from the board's column. The two stores may be one repository or two.
- **`logbook` knows nothing of the board.** Its `done` no longer suggests `next drop`.
- **For one person first.** A board shared by a team — several people pulling, assignees, concurrent writes — is a later item.
- *(agent's call)* **The skill keeps its name and triggers**: `/next`, "what's next", "was steht an". Only what it reads and prints changes.
- *(agent's call)* **A write refreshes the cards it touches**: `put`, a pull and a close read the title fresh from the item they write. `show` changes nothing; a card whose title no longer matches its item is reported as a contradiction.
- *(agent's call)* **A board that is configured but cannot be written** — resolve fails for another reason than "not configured", the contract is missing, the push is rejected — is reported in the `backlog-ops` summary; the pull or close itself stands. "Not configured" (the store script's exit 2) is silent.
- *(agent's call)* **An item In Progress without a card is not a contradiction.** A close is staged on the feature branch and reaches the default branch with the merge, while the card leaves the board at the close; `next` reads items at `origin/HEAD` (ADR-0010). Every item would be reported for as long as its pull request is open. Since every pull makes a card, the check would catch almost nothing else.
- *(agent's call)* **A close inside a worktree of the store's own repository commits the board change on that feature branch.** `store resolve` uses a checkout whose `origin` is the store's remote as it is (ADR-0007), as it already does for a log line. The card then leaves the board with the merge, like the item's Done. A conflict in the board file on rebase is resolved like any other.
- *(agent's call)* **Only work gets a card.** A pull that cascades to an epic moves the pulled item's card, not the epic's; the ongoing refinement item never gets one — the same rule as `backlog.py show --in-progress`.

**Design**:

*The store's contract (section `Board`)* names, as the `Next` section does today: where the board is, its columns, the card format — including how the item link is built from the repo registry — the order within each column, the commit subject of a change, the language. The skills ship none of it.

*`next`*:
- Resolves `BOARD`, reads the contract section `Board`, reads the items as in XAS-040 (fetched, never pulled — ADR-0010).
- `show` prints the board as a table with the same two columns; each card carries status and priority read fresh from its item. Below it, the contradictions: a card whose item is Done or Superseded; a card in In Progress whose item is not In Progress; a card whose title differs from its item's; an address that resolves to no item or a repo missing from the registry; an item that does not parse; a repo left out.
- `put` places or moves a card in *Next* ("next" = top, "after X", "at n"). A card that is in In Progress is not moved back by `put` — that is a reverse transition; say so and stop.
- `drop` removes a card from either column.
- Every change is one commit in the store, pushed (`store commit-push`).

*`backlog-ops`*:
- After the pull's own commit and push (or after it stays staged, as XAS-041 decides), and after `set-status <ID> Done` on a close: resolve `BOARD`, read the contract, move the card — into In Progress on a pull (out of *Next* if it was there, newly made otherwise), off the board on a close. One commit in the store, pushed. The consuming repository is not touched by this step.
- The summary names the board move, or why there was none.
- `allowed-tools` gains `Bash(${CLAUDE_PLUGIN_ROOT}/scripts/store *)`.
- The direction rule holds: no repository names the board; the machine's settings do.

*`logbook`*: `done` step 4 (the `next drop` suggestion) and the `next` integration point go.

*Architecture and record*: `docs/architecture.md` — the skill map and the sequence "What comes next" — follows the change (via `design-record`). Whether "`backlog-ops` writes into a configured store" is an ADR of its own — it changes the line in `architecture.md` that `backlog-ops` never leaves the consuming repo — is decided in `design-record`'s three-part test.

**Rollout**: ZK-049b switches the store's contract from `Next` to `Board` and renames the file. Between that commit and the plugin release, an installed `next` stops with "section missing" — so both land the same day, the store first.

**Acceptance Criteria**:
- [ ] `next show` prints the board from the store named by `BOARD_PATH`/`BOARD_REMOTE` as a two-column table, with status and priority per card, and the contradictions listed above; with only `LOGBOOK_*` set it stops with the store script's message
- [ ] `next put` and `next drop` change the board file in the contract's format, one commit each, pushed
- [ ] With a board configured, `backlog-ops` pull puts the card into In Progress — moved from *Next* or newly made — and close takes it off, one store commit each; the consuming repository's `git status` is unchanged by that step
- [ ] Without a board configured, `backlog-ops` pull and close behave exactly as before, with no extra output
- [ ] Neither `next` nor `backlog-ops` names `LOGBOOK` or the log; `logbook` no longer names `next`
- [ ] No skill file names a specific store, path or remote
- [ ] `docs/architecture.md` matches; an ADR exists if `design-record` finds one is due
- [ ] Plugin version bumped (minor) in `plugin.json` and `marketplace.json`
- [ ] End-to-end against the author's Kasten: pull an item in another repo → its card is in In Progress on Gitea; close it → the card is gone
- [ ] `uv run --group dev pytest` green; both CI matrix jobs green
