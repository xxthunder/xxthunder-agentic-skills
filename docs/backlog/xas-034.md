# [XAS-034] `zettelkasten` skill: consult and feed a personal learnings repo from any session

**Status**: Open
**Priority**: High
**Component**: `plugins/xxthunder-dev-skills/skills/zettelkasten/` (new),
`plugins/xxthunder-dev-skills/.claude-plugin/plugin.json`,
`.claude-plugin/marketplace.json`, `docs/architecture.md`, `tests/dev/`

**Related**: [XAS-027](xas-027.md) organises design artifacts by lifetime and
stops at "as long as the product". This item adds the row beyond it — what
outlives the repo — and the place it goes. [ADR-0006](../adr/0006-record-locations-are-discovered.md)
resolves record locations by discovery; this skill deliberately does not, see
Scope Decisions. [XAS-030](xas-030.md) set the check applied before adding a
skill: what does it carry that nothing else does?

**Summary**:
As a maintainer working across many repositories with a coding agent, I want a
learning that survives a project — and a chronicle of what I started and
finished — to land in one personal Zettelkasten repo from whichever session
produced it, without any of my repositories knowing that Zettelkasten exists,
so that the next session on any repo starts already knowing what earlier ones
learned.

**Description**:
Agentic sessions produce two things that have no home in the repo they happen
in. The first is a **learning**: a correction the author made, a limit a tool
turned out to have, a rule that would have made an earlier session go
differently — true after the project is deleted, so it does not belong in the
project's ADRs or `CLAUDE.md`. The second is the **chronicle**: what was started
and what was finished, across repos. `git log` holds it per repo; nothing holds
it across them.

Both have a natural home: a personal Zettelkasten — a git repo of atomic notes
in the author's own words. Today nothing carries them there. Learnings stay in
the transcript and the transcript ends. The Zettelkasten fills only when the
author sits down to distil, which is a separate step that does not happen.

**What exists already, and why it does not cover this.** Checked before filing,
per the [XAS-030](xas-030.md) rule:

- Claude Code's auto-memory is per workspace and per machine, written by the
  agent for the agent. It is not the author's words and it does not cross repos.
- `claude-md-management` (official) captures session learnings into the
  **consuming repo's** `CLAUDE.md` — the one place this item rules out.
- `remember` (official marketplace, third-party) extracts and compresses
  conversations into daily logs automatically, into its own store. Automatic
  summarisation is the opposite of "in the author's own words", and it does not
  write to a repo of the author's choosing under that repo's conventions.
- `retrospective` in this plugin ends at the project's guidelines. It answers
  "what should this repo do differently"; it never asks "what holds beyond it".

Nothing carries a curated, author-owned learning out of a session into a
cross-repo notes repo. That is the gap.

**The direction rule** that shapes everything else: **the Zettelkasten points
into repositories; no repository points into the Zettelkasten.** A learning
cites the repo, item ID and date it came from. But no `CLAUDE.md`, no
`AGENTS.md`, no backlog item and no skill text in a consuming repo names the
Zettelkasten, its path or its remote — some of those repos are public. What
knows the Zettelkasten is the **machine**: the skill's configuration in the
user's settings, and the agent's per-workspace memory.

**Configuration**, user-level (`~/.claude/settings.json` → `env`), never in a
consuming repo:

- `ZETTELKASTEN_PATH` — a local checkout, used when present.
- `ZETTELKASTEN_REMOTE` — cloned into a scratch directory when no checkout is
  present (ephemeral devcontainers).

Resolution order: the current directory *is* the Zettelkasten → use it as-is;
`ZETTELKASTEN_PATH` exists → `git pull --ff-only`, then use it; otherwise clone
`ZETTELKASTEN_REMOTE`; nothing configured → say so and stop. The skill never
guesses. Authentication (SSH keys, `GIT_SSH_COMMAND`) is the environment's
business, not the skill's.

**The rules live in the Zettelkasten, not in the skill.** The skill reads the
Zettelkasten's own `AGENTS.md` and follows the section headed `Workflow` there:
where the log is, where learnings go, the log line format, the learning
template, the tests a learning has to pass, the language. The only thing the
skill hardcodes is that this section exists and names those things. A
Zettelkasten that changes its log format changes its `AGENTS.md`; the plugin
does not ship a new version. This is the same seam `design-record` uses — the
consumer's record states its own rules — applied one repo further out.

**Three operations**, `/zettelkasten start|capture|done`, or the natural
phrases the skill lists:

- **`start`** — at the start of a topic (pulling an item, refining, "let's work
  on X"). Resolve the Zettelkasten fresh. Look up the same address
  (`<repo> <ITEM-ID>`) in the log — "you started this on …" — and search the
  learnings for the topic's terms (item title, component names, tags). Present
  up to five hits as one-liners with links; the agent carries them as context
  for the session. Prepend a `started` line, unless one already exists for this
  address without a later `done` (resumption is not a new start). Record the
  per-workspace memory that this workspace runs the Zettelkasten workflow.
- **`capture`** — at any time; the agent also proposes it when the author
  corrects it, or when a result plainly outlives the repo. Run the
  Zettelkasten's tests for a learning out loud, in the chat. **The author words
  the claim.** The agent drafts the rest from the template — origin, reasoning,
  consequence — marked as its contribution. Write the learning, add it to the
  hub, prepend a `captured` line. A candidate the author cannot yet word goes
  where the Zettelkasten's `AGENTS.md` says unfinished captures go, with no log
  line.
- **`done`** — an item closed or a milestone reached. Prepend a `done` line
  with the one-line result and links to the notes involved. Then ask, **once**:
  "Does anything here outlive this repo?" — yes leads to `capture`. This is
  how the capture question reaches the end of an item without touching
  `backlog-ops`, which closes items exactly as before.

Every log line is one commit, pushed immediately. In an ephemeral container an
unpushed line is not a line.

**The memory.** The first `start` in a workspace leaves a project memory:
*this workspace runs the Zettelkasten workflow*. In later sessions the agent
invokes `start` when a topic begins and `done` when an item closes, unprompted.
It is a memory, not a hook — "no Zettelkasten here" deletes it. It is also per
machine: a fresh devcontainer knows nothing until the author says `start` once
there. A user-level hook would be more robust and is more machinery; it is not
built until forgetting proves to be a problem.

**What the skill never does:** write into the consuming repo; create a learning
without the author's wording; edit an existing log line; run without
configuration; mention any specific Zettelkasten in its own text.

**Scope Decisions**:
- **Configured, not discovered — a considered divergence from
  [ADR-0006](../adr/0006-record-locations-are-discovered.md).** That ADR resolves
  record locations by discovery because the record lives *in* the consuming
  repo. The Zettelkasten must not be discoverable from the consuming repo —
  that is the direction rule — so there is nothing to discover, and machine-level
  configuration is the only place left. Candidate for an ADR at close under the
  three-part test: it outlives the change, it could have gone the other way
  (a dotfile in the repo, gitignored), and the code will not explain why not.
- **The consumer's `AGENTS.md` is the contract.** Format rules for the log and
  the learnings are the Zettelkasten's, stated once, there. The skill ships no
  template and no line format of its own. Second ADR candidate, same test.
- **Deterministic parts get a script; judgment stays prose.** Resolving the
  Zettelkasten, and inserting a line under today's date header without creating
  a duplicate `started`, are mechanics with a right answer — they live in a
  helper script with tests, per the *Code changes ship with tests* rule in
  `CLAUDE.md`. Searching, running the tests for a learning, drafting from the
  template are judgment and stay in `SKILL.md`.
- **Named `zettelkasten`** because that names the method, not any particular
  repo. No alias.
- **Minor version bump** of `xxthunder-dev-skills`: a new skill, no breaking
  change.

**Acceptance Criteria**:
- [ ] `SKILL.md` describes the three operations, the resolution order, the
      `AGENTS.md` `Workflow` contract, the direction rule and the never-list;
      its trigger description names `start`, `capture`, `done` and the natural
      phrases
- [ ] Helper script resolves the Zettelkasten (cwd → `ZETTELKASTEN_PATH` →
      `ZETTELKASTEN_REMOTE` → stop) and inserts a log line under the right date
      header, newest first, without duplicating an open `started`; tests cover
      each branch and the duplicate case
- [ ] Negative control: with neither variable set and outside a Zettelkasten,
      the skill stops with a message — a test asserts it does not silently
      succeed
- [ ] `grep -ri` over the skill directory finds no path, remote or name of any
      specific Zettelkasten
- [ ] `plugin.json` and `marketplace.json` bumped (minor); `README.md` and
      `CLAUDE.md` skill lists updated
- [ ] `docs/architecture.md`: the skill added to the components diagram and a
      *Capturing a learning* key flow, via `design-record`
- [ ] Verified end to end from a consuming repo that is not the Zettelkasten:
      `start` shows a prior log line and at least one learning hit, `done`
      leads to a `capture`, the learning and both log lines are pushed — and the
      consuming repo's working tree is untouched (`git status` clean there)

**Out of scope**:
- The Zettelkasten's own conventions — log format, learning template, the
  tests a learning must pass, its language rules. They belong to the
  Zettelkasten and are read from its `AGENTS.md`.
- Any change to `backlog-ops` or `retrospective`.
- A user-level hook to invoke `start` automatically.
