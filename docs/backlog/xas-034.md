# [XAS-034] `learnings` skill: capture what outlives a repo into a personal knowledge repo

**Status**: In Progress
**Priority**: High
**Component**: `plugins/xxthunder-dev-skills/skills/learnings/` (new),
`plugins/xxthunder-dev-skills/scripts/` (new — shared store resolver),
`plugins/xxthunder-dev-skills/.claude-plugin/plugin.json`,
`.claude-plugin/marketplace.json`, `docs/architecture.md`, `docs/adr/`,
`tests/dev/`

**Related**: [XAS-035](xas-035.md) is the sibling `logbook` skill — the
chronicle half of what was originally one `zettelkasten` item. It is built
second, reuses the store resolver and the two ADRs from this item, and its
`done` hands off to `capture` here. [XAS-027](xas-027.md) organises design
artifacts by lifetime and stops at "as long as the product"; this item adds
the row beyond it. [ADR-0006](../adr/0006-record-locations-are-discovered.md)
resolves record locations by discovery; this skill deliberately does not, see
Scope Decisions. [XAS-030](xas-030.md) set the check applied before adding a
skill: what does it carry that nothing else does?

**Summary**:
As a maintainer working across many repositories with a coding agent, I want a
learning that survives a project to land in one personal knowledge repo from
whichever session produced it, without any of my repositories knowing that
repo exists, so that the next session on any repo can start already knowing
what earlier ones learned.

**Description**:
Agentic sessions produce **learnings** that have no home in the repo they
happen in: a correction the author made, a limit a tool turned out to have, a
rule that would have made an earlier session go differently. A learning is
true after the project is deleted, so it does not belong in the project's ADRs
or `CLAUDE.md`. Its natural home is a personal knowledge repo — a git repo of
atomic notes in the author's own words; a Zettelkasten, a second brain,
whatever the author runs. Today nothing carries a learning there. It stays in
the transcript and the transcript ends. The knowledge repo fills only when the
author sits down to distil, which is a separate step that does not happen.

**What exists already, and why it does not cover this.** Checked before filing,
per the [XAS-030](xas-030.md) rule:

- Claude Code's auto-memory is per workspace and per machine, written by the
  agent for the agent. It is not the author's words and it does not cross repos.
- `claude-md-management` (official) captures session learnings into the
  **consuming repo's** `CLAUDE.md` — the one place this item rules out.
- `remember` (official marketplace, third-party) extracts and compresses
  conversations into daily logs automatically, into its own store. Automatic
  summarisation is the opposite of "in the author's own words", and it does not
  write to a repo of the author's choosing under that repo's conventions.
- `retrospective` in this plugin ends at the project's guidelines. It answers
  "what should this repo do differently"; it never asks "what holds beyond it".

Nothing carries a curated, author-owned learning out of a session into a
cross-repo knowledge repo. That is the gap.

**The direction rule** that shapes everything else: **the knowledge repo points
into repositories; no repository points into the knowledge repo.** A learning
cites the repo, item ID and date it came from. But no `CLAUDE.md`, no
`AGENTS.md`, no backlog item and no skill text in a consuming repo names the
knowledge repo, its path or its remote — some of those repos are public. What
knows the knowledge repo is the **machine**: the skill's configuration in the
user's settings.

**Configuration**, user-level (`~/.claude/settings.json` → `env`), never in a
consuming repo:

- `LEARNINGS_PATH` — a local checkout, used when present.
- `LEARNINGS_REMOTE` — cloned into a scratch directory when no checkout is
  present (ephemeral devcontainers).

Resolution order: the current directory *is* the store (it is `LEARNINGS_PATH`,
or its `origin` is `LEARNINGS_REMOTE`) → use it as-is; `LEARNINGS_PATH` exists
→ `git pull --ff-only`, then use it; otherwise clone `LEARNINGS_REMOTE`;
nothing configured → say so and stop. The skill never guesses. Authentication
(SSH keys, `GIT_SSH_COMMAND`) is the environment's business, not the skill's.

The `logbook` ([XAS-035](xas-035.md)) has its own pair, `LOGBOOK_PATH` and
`LOGBOOK_REMOTE`. The two stores may be one repo or two; the skills do not
assume either.

**The rules live in the store, not in the skill.** The skill reads the store's
own `AGENTS.md` and follows the section headed `Learnings` there: where
learnings go, the note template, the hub or index a new note is added to, the
tests a learning has to pass, the language. The only thing the skill hardcodes
is that this section exists and names those things. A store that changes its
template changes its `AGENTS.md`; the plugin does not ship a new version. This
is the same seam `design-record` uses — the consumer's record states its own
rules — applied one repo further out.

**Two operations**, `/learnings capture|recall`, or the natural phrases the
skill lists:

- **`capture`** — at any time. The agent also proposes it when the author
  corrects it, when a result plainly outlives the repo, or when `logbook done`
  asks its one question. Resolve the store fresh. Run the store's tests for a
  learning out loud, in the chat. **The author words the claim.** The agent
  drafts the rest from the store's template — origin (repo, item ID, date),
  reasoning, consequence — marked as its contribution. Write the note, add it
  to the hub, commit, push. A candidate the author cannot yet word goes where
  the store's `AGENTS.md` says unfinished captures go.
- **`recall`** — at the start of a topic, or on "what do I know about X".
  Resolve the store fresh and search the learnings for the topic's terms (item
  title, component names, tags). Present up to five hits as one-liners with
  links; the agent carries them as context for the session. `logbook start`
  suggests it; nothing else triggers it unprompted.

Every capture is one commit, pushed immediately. In an ephemeral container an
unpushed note is not a note.

**What the skill never does:** write into the consuming repo; create a learning
without the author's wording; run without configuration; mention any specific
store in its own text.

**Scope Decisions**:
- **Configured, not discovered — a considered divergence from
  [ADR-0006](../adr/0006-record-locations-are-discovered.md).** That ADR resolves
  record locations by discovery because the record lives *in* the consuming
  repo. The knowledge repo must not be discoverable from the consuming repo —
  that is the direction rule — so there is nothing to discover, and machine-level
  configuration is the only place left. ADR at close, under the three-part
  test: it outlives the change, it could have gone the other way (a dotfile in
  the repo, gitignored), and the code will not explain why not.
- **The store's `AGENTS.md` is the contract.** Format rules for the learnings
  are the store's, stated once, there. The skill ships no template of its own.
  Second ADR at close, same test. Both ADRs are written for the general case —
  *a cross-repo store the skill writes to* — so `logbook` cites them rather
  than writing its own.
- **One store resolver, shared, at plugin level.** Resolving a store from a
  variable pair, and committing-and-pushing a result (with one `pull --rebase`
  retry on a rejected push), are mechanics with a right answer and are needed
  by both skills. They live in one helper script under
  `plugins/xxthunder-dev-skills/scripts/`, parameterised by variable prefix
  (`LEARNINGS`, `LOGBOOK`), with tests per branch, per the *Code changes ship
  with tests* rule in `CLAUDE.md`. Plugin-level executable code is a new
  convention for this plugin — `hooks/` is the precedent — and
  `docs/architecture.md` records it. Running the store's tests for a learning
  and drafting from the template are judgment and stay in `SKILL.md`.
- **Triggered by description, not by memory.** The moments that call for
  `capture` — a correction, a result that outlives the repo, the `done`
  question — are named in the skill's trigger description. No per-workspace
  memory, no hook. The original item's memory mechanism went with the
  chronicle half and is reconsidered in [XAS-035](xas-035.md).
- **Named `learnings`** because that names what is captured, not the method
  the store runs (Zettelkasten, second brain, …) and not any particular repo.
  No alias.
- **Split from the chronicle.** The original item bundled `start`/`done` log
  lines with `capture`. They write to different stores under different rules,
  and only the chronicle has a log format, a duplicate check and a trigger
  problem. Splitting keeps this item free of all three.
- **Minor version bump** of `xxthunder-dev-skills`: a new skill, no breaking
  change.

**Acceptance Criteria**:
- [x] `SKILL.md` describes `capture` and `recall`, the resolution order, the
      `AGENTS.md` `Learnings` contract, the direction rule and the never-list;
      its trigger description names `capture`, `recall` and the natural
      phrases, including the correction and outlives-the-repo moments
- [x] Shared helper script under `plugins/xxthunder-dev-skills/scripts/`
      resolves a store by variable prefix (cwd → `<PREFIX>_PATH` →
      `<PREFIX>_REMOTE` → stop) and commits-and-pushes a result with one
      rebase retry; tests cover each resolution branch, the retry and the
      give-up case
- [x] Negative control: with neither variable set and outside a store, the
      skill stops with a message — a test asserts the resolver does not
      silently succeed
- [x] `grep -ri` over the skill and scripts directories finds no path, remote
      or name of any specific store
- [x] Two ADRs via `design-record`: *cross-repo stores are configured, not
      discovered* and *the store's `AGENTS.md` is the contract*, each written
      for the general case
- [x] `docs/architecture.md` via `design-record`: the skill added to the
      components diagram, a *Capturing a learning* key flow, and the
      plugin-level `scripts/` convention
- [x] `plugin.json` and `marketplace.json` bumped (minor); `README.md` and
      `CLAUDE.md` skill lists updated
- [ ] Verified end to end from a consuming repo that is not the store:
      `recall` shows at least one hit, `capture` writes a learning that is
      pushed — and the consuming repo's working tree is untouched
      (`git status` clean there)

**Out of scope**:
- The store's own conventions — note template, hub, the tests a learning must
  pass, its language rules. They belong to the store and are read from its
  `AGENTS.md`.
- The chronicle — `start`, `note`, `done` — which is [XAS-035](xas-035.md).
- Any change to `backlog-ops` or `retrospective`.
- Any hook or memory that invokes `capture` or `recall` unprompted.
