# [XAS-036] Cross-repo stores: the working repository may be the store, and a failed pull says why

**Status**: Open
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/skills/learnings/SKILL.md`,
`plugins/xxthunder-dev-skills/skills/logbook/SKILL.md`,
`plugins/xxthunder-dev-skills/scripts/store`, `tests/dev/scripts/test_store.py`,
`plugins/xxthunder-dev-skills/.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`

**Related**: [XAS-034](xas-034.md) (`learnings` and the shared resolver),
[XAS-035](xas-035.md) (`logbook`)

**Summary**:
As an author whose notes repository is both the logbook and the learnings store, I want the
two skills to say plainly that the store may be the repository I am working in, and the
resolver to report the real reason when a pull fails, so that neither the skill text nor the
error message sends me in the wrong direction.

**Description**:

Two defects, found while one notes repository was set up as both stores on 2026-09-24.

**1. `learnings` contradicts its own design.** [XAS-034](xas-034.md) makes "the current
directory *is* the store" the first step of the resolution order, and Step 6 of
`learnings/SKILL.md` handles that case ("When the store *is* the working repository …").
But line 15 of the same file says: "The store is never the repository the session is
working in." Both skill descriptions also say "Never writes into the current repository"
without the exception. `logbook/SKILL.md` states the exception in its body ("The logbook may
be the repository the session is working in"); `learnings` does not. An agent that reads
line 15 refuses a configuration the resolver supports.

**2. A failed pull is reported as a diverged branch.** `store resolve` runs
`git pull -q --ff-only` on a configured checkout (line 75) and on the cached clone (line 88).
With `pull.rebase=true` in the user's git config, git takes the rebase path, and a rebase
refuses to start while the checkout has uncommitted changes. The script then prints
"cannot fast-forward … — the checkout has diverged from its remote; resolve it by hand",
which is not the cause. Reproduced with a throwaway store on 2026-09-24, Git for Windows:

| `pull.rebase` | Store checkout | `store resolve` |
|---|---|---|
| `true` | one modified, uncommitted file; no new commits upstream | exit 1, "has diverged from its remote" |
| `false` | the same | exit 0, the path |

This hits exactly the setup above: while a session in the notes repository has uncommitted
work, a session in any other repository cannot write a log line or a learning.

**Acceptance Criteria**:

- [ ] `learnings/SKILL.md` no longer says that the store is never the working repository.
      Its description, its introduction and "What This Skill Never Does" agree with the
      resolution order and Step 6: when the store is the working repository, the capture
      commits only its own files, and whatever else is staged stays staged.
- [ ] The `logbook` description states the same exception as its body.
- [ ] Both pulls in `store` fast-forward without a rebase, whatever `pull.rebase` is set to
      (for example `git pull -q --ff-only --no-rebase`). A test with `pull.rebase=true` and
      an uncommitted change in the store checkout resolves with exit 0.
- [ ] When a pull still fails, the message carries git's own reason and does not guess
      "diverged". A test covers a real divergence and a blocked pull, and the two messages
      differ.
- [ ] The plugin version is bumped as a patch in both manifests.

**Scope Decisions**:

- **Never stash or reset the author's work.** A pull that incoming changes cannot pass
  without touching an uncommitted file still fails. The fix is an honest message, not a
  cleverer pull.
- **No change to the resolution order.** Case 1 is wrong text, not wrong behaviour.
- **One item, two defects.** Both come from the same configuration and touch the same few
  files; split them if one is picked up alone.
