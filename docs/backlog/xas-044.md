# [XAS-044] Requirements as a binding design artifact where sphinx-needs is in use

**Status**: Open
**Priority**: Medium
**Component**: `docs/adr/`, `plugins/xxthunder-dev-skills/scripts/backlog.py`, `plugins/xxthunder-dev-skills/skills/refinement/references/backlog-format.md`, `plugins/xxthunder-dev-skills/skills/design-record/`, `plugins/xxthunder-dev-skills/skills/backlog-ops/`, a read-only requirements scan (new)
**Related**: [XAS-027](xas-027.md) (the design record this extends), shortcuts SC-073 (first consumer, px-proxy slice)

**Summary**:
As the maintainer of a repository that uses sphinx-needs, I want requirements as a third binding design artifact, changed by stories and traced to by code and tests, so that a trace into the code points at what the product does now and not at a closed item.

**Description**:
[ADR-0001](../adr/0001-two-design-artifacts-split-by-lifetime.md) keeps two binding design artifacts, the ADR log and `architecture.md`. It rejected a standing requirements document for two reasons: it duplicates a story's Summary and Acceptance Criteria, and staying truthful would need bidirectional traceability machinery that was out of scope.

In a repository that uses sphinx-needs with ubCode and sphinx-codelinks, that machinery exists: needs with IDs, typed links, checks that fail a build, traces from code comments and from test reports. The second reason no longer holds there. The first falls to ADR-0001's own sorting rule, lifetime: an acceptance criterion verifies one change and is no longer maintained after Done; a requirement states current behaviour and stays true. The same split already separates an item's Scope Decisions from `architecture.md`.

Why it matters: code that traces to a story traces to history. In shortcuts, SC-040 decided that px does not start at logon, and SC-067 reversed that (shortcuts ADR-0005). A code marker pointing at SC-040 is silently wrong today. A marker pointing at the autostart requirement stays right, and both items link to that requirement.

Raised on 2026-10-23 at the useblocks user day, together with shortcuts SC-073.

**Scope Decisions**:
- **Only where sphinx-needs is in use**: a `ubproject.toml` at the repository root switches all of this on. It is the single configuration ubCode, `ubc` and Sphinx (through `needs_from_toml`) read, as in useblocks/SPLed. Without it, ADR-0001 holds unchanged.
- **Requirements are native MyST needs**, edited in place like `architecture.md`. Where the files live and how they are split (per tool, per component) is the consuming repository's choice.
- **One writer** ([ADR-0003](../adr/0003-one-writer-for-the-design-record.md)): `design-record` writes requirements, as it writes ADRs and `architecture.md`. A read-only scan proposes; applying goes through `design-record`.
- **Direction of traces**: stories link to the requirements they change; ADRs link to the requirements they constrain; code and tests link to requirements. Nothing in the code links to a story: the commit already records which change touched it.
- **Closing an item updates the requirements**: its behaviour criteria are the delta. The agent drafts the requirement change, the author approves it, as with an ADR body. Chores, refactors, backlog fixes and superseded items change no requirement and say so explicitly.
- **Item and ADR headers become needs**: only the header block turns into a need directive; Summary, Description, Scope Decisions and criteria stay plain Markdown below it. ubCode indexes native needs while editing, and no generator has to track the item format. One explicit migration converts all items and ADRs of a repository at once, so a repository never holds both formats.
- **Bootstrap from what is true now**: the scan proposes requirements from code, tests and user docs, then maps closed items onto them. It does not replay stories, whose deltas include reversed and superseded decisions. Where it cannot tell which requirement an old item changed, it says so ([ADR-0005](../adr/0005-bootstrap-architecture-never-reconstruct-adrs.md): omission beats invention).
- **Only what both readers understand**: Sphinx and ubCode read the same `ubproject.toml`; the skills use no Sphinx-only directive or needs function.
