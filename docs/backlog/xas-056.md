# [XAS-056] `evals/` is checked against skill-creator's eval tooling: keep, align or replace

**Status**: In Progress
**Priority**: Medium
**Component**: `evals/`, `tests/evals/`, `CONTRIBUTING.md` (Behavioural evals)
**Related**: [XAS-054](xas-054.md) (the ADR takes this item's result), [XAS-047](xas-047.md)
and ADR-0012 (why `evals/` exists), [XAS-049](xas-049.md), [XAS-050](xas-050.md)

**Summary**:
As the maintainer, I want to know whether `skill-creator` already does what `evals/` does,
so that we keep our own harness only where it does something `skill-creator` cannot.

**Description**:
XAS-047 built `evals/`, which exports the plugin at a git ref, builds a sandbox with a store
and a consumer repo on local bare remotes, runs `claude -p` and grades the end state with
plain assertions. Nobody checked first what `skill-creator` ships:

- `run_eval.py` and `run_loop.py`
- `aggregate_benchmark.py` and `generate_report.py`
- `improve_description.py` for trigger optimisation
- the agents `grader`, `comparator` (blind A/B) and `analyzer`

The author's principle applies after the fact too: we are not the first with this problem.
The principles are timeless, so they also cover work that is already merged.

Likely differences to check, not yet verified:
- `evals/` grades git state across two repos (commits on remotes, the board, the log).
  `skill-creator` likely grades outputs and transcripts.
- The `skill-creator` grader is an LLM, which ADR-0012 rejected for grading runs. Its other
  job, critiquing weak assertions, may still fit.
- `improve_description.py` addresses exactly what XAS-051 fixed by hand: a description that
  did not trigger.

**Comparison** (agent, 2026-10-31, read from `skill-creator` as installed):

| Part | `skill-creator` | `evals/` | Call |
|---|---|---|---|
| Running a case | The agent in the session spawns subagents with and without the skill; there is no headless runner for task cases (`run_eval.py` tests triggering only) | Headless `claude -p` per run, against the plugin exported at a git ref, in a sandbox with its own store and consumer repo on bare remotes; no user settings, no MCP, store variables cleared | **Keep** `evals/`: a subagent inside the session cannot pin the plugin to a ref or isolate the stores |
| Baseline | With and without the skill, or a snapshot of the old version, side by side in each iteration | `--ref develop` and `--ref <branch>`, run and reported separately | **Keep**; a case that passes on both refs is non-discriminating — checking that is mechanical and belongs to the gate ([XAS-049](xas-049.md)) |
| Grading | A grader agent per run; for anything checkable it says to write a script instead | Python assertions only (ADR-0012) | **Keep**; `skill-creator` agrees for checkable assertions |
| Critique of the evals | The grader flags weak assertions; the analyzer flags non-discriminating and flaky ones | Every case is unit-tested to fail on the untouched sandbox and pass on its expected end state | **Align**: the analyzer's two signals are mechanical — passes on both refs (XAS-049), mixed pass rates (already in `report`) |
| Cost metrics | `timing.json` per run; benchmark with mean ± stddev for time and tokens | None | **Align**: the `result` event of each run carries duration and cost; record and report them — XAS-055 needs the cost of a loop round |
| Human review | An HTML viewer with a feedback form | `output.md`, `stream.jsonl`, `result.json` per run, `report` | **Leave out**; the transcripts are enough for now |
| Blind A/B and post-hoc analysis | `comparator` and `analyzer` agents judge which version's output is better | None | **Leave out**; our skills change state, which assertions check, not output quality |
| Triggering | `run_eval.py` / `run_loop.py` / `improve_description.py`: 20 queries per skill with near misses, three runs each, train/test split, up to five rounds | Only incidentally, where a case checks which skill was invoked | **Adopt as a tool**, run from its plugin, not vendored. Caveats: it loads the user's own settings and plugins, it tests the description as a project command rather than through the plugin, and it uses `select` on pipes (POSIX only) |
| Validation | `quick_validate.py`: frontmatter keys, kebab-case name, description ≤ 1024 characters, no angle brackets | None | **Align**: a test over every `SKILL.md`. Run once on 2026-10-31: 7 of 9 dev skills carry `user_invocable`, which is not a frontmatter key, and `naps2-scan`'s description has 1032 characters |

**Acceptance Criteria**:
- [x] A comparison, recorded in this item: what `skill-creator` covers, what only `evals/`
      covers, and what neither covers
- [ ] A decision for each part — keep, align with `skill-creator`, or replace with it —
      handed to the ADR of [XAS-054](xas-054.md)
- [ ] The trigger descriptions of the dev skills are run once through
      `improve_description.py` (or its equivalent), and the result is recorded as findings
- [x] What is decided to be replaced or aligned has an item of its own: [XAS-057](xas-057.md)

      non-discrimination check in [XAS-049](xas-049.md)
