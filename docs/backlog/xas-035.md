# [XAS-035] `logbook` skill: chronicle what each session starts, notes and finishes, across repos

**Status**: Open
**Priority**: High
**Component**: `plugins/xxthunder-dev-skills/skills/logbook/` (new),
`plugins/xxthunder-dev-skills/scripts/` (shared store resolver, from
[XAS-034](xas-034.md)), `plugins/xxthunder-dev-skills/skills/backlog-ops/SKILL.md`
(only if the trigger decision below lands there),
`plugins/xxthunder-dev-skills/.claude-plugin/plugin.json`,
`.claude-plugin/marketplace.json`, `docs/architecture.md`

**Related**: [XAS-034](xas-034.md) is the sibling `learnings` skill — the
other half of what was originally one `zettelkasten` item. It is built first
and provides the shared store resolver and the two ADRs this skill relies on
(*configured, not discovered*; *the store's `AGENTS.md` is the contract*).
`start` here suggests its `recall`; `done` here hands off to its `capture`.
[ADR-0004](../adr/0004-always-on-rule-is-orientation-not-enforcement.md)
records that hooks are Claude Code-specific while skills port, which bears on
the trigger decision below. [XAS-030](xas-030.md) set the check applied before
adding a skill: what does it carry that nothing else does?

**Summary**:
As a maintainer working across many repositories with a coding agent, I want
what each session started, noted and finished to land in one personal logbook
repo from whichever session did it, without any of my repositories knowing
that repo exists, so that I have one chronicle across repos instead of one
`git log` per repo.

**Description**:
Agentic sessions produce a **chronicle**: what was started, what was noted
along the way, what was finished — across repos. `git log` holds it per repo;
nothing holds it across them. Its natural home is a personal logbook — a git
repo with a dated log in the author's conventions. Today nothing writes to it
from a session; the chronicle is reconstructed, if at all, from several repos'
histories.

**What exists already, and why it does not cover this.** Checked before filing,
per the [XAS-030](xas-030.md) rule:

- `git log` and GitHub's activity view are per repo, and record commits, not
  what a session set out to do or what it found on the way.
- `remember` (official marketplace, third-party) writes daily logs, but by
  automatic summarisation of the conversation into its own store — not one
  line per event in the author's log, under the author's format.
- `backlog-ops` transitions items in the consuming repo's backlog. That is the
  per-repo record; it does not cross repos and must not, see the direction rule.

Nothing writes a one-line chronicle entry from a session into a cross-repo
logbook. That is the gap.

**The direction rule** is inherited from [XAS-034](xas-034.md) unchanged: the
logbook points into repositories; no repository points into the logbook. A log
line cites the repo and item ID it is about. No file in a consuming repo names
the logbook, its path or its remote. What knows the logbook is the machine.

**Configuration**, user-level (`~/.claude/settings.json` → `env`), never in a
consuming repo: `LOGBOOK_PATH` and `LOGBOOK_REMOTE`, resolved by the shared
resolver from [XAS-034](xas-034.md) with the same order (cwd is the store →
`LOGBOOK_PATH` → `LOGBOOK_REMOTE` → stop). The logbook and the learnings store
may be one repo or two; this skill does not assume either.

**The rules live in the logbook, not in the skill.** The skill reads the
logbook's own `AGENTS.md` and follows the section headed `Logbook` there:
where the log is, how days are headed, whether newest is first, the line
format for `started`, `note` and `done`, the language. The only thing the
skill hardcodes is that this section exists and names those things.

**Three operations**, `/logbook start|note|done`, or the natural phrases the
skill lists:

- **`start`** — at the start of a topic (pulling an item, refining, "let's
  work on X"). Resolve the logbook fresh. Look up the same address
  (`<repo> <ITEM-ID>`) in the log — "you started this on …". Add a `started`
  line, unless one already exists for this address without a later `done`
  (resumption is not a new start). Then suggest `learnings recall` for the
  topic's terms.
- **`note`** — at any time: one line about what was done or found while
  working, in the author's words or the agent's, confirmed by the author
  before it is written.
- **`done`** — an item closed or a milestone reached. Add a `done` line with
  the one-line result and links to what was involved. Then ask, **once**:
  "Does anything here outlive this repo?" — yes leads to `learnings capture`.
  This is how the capture question reaches the end of an item without
  `backlog-ops` knowing that learnings exist.

Every line is one commit, pushed immediately through the shared resolver's
commit-and-push, which retries once after `pull --rebase` on a rejected push.
Two sessions on two machines prepending under the same date header can still
conflict on that retry; the skill reports the conflict and stops rather than
resolving it. In an ephemeral container an unpushed line is not a line.

**What the skill never does:** write into the consuming repo; edit an existing
log line; run without configuration; mention any specific logbook in its own
text.

**Scope Decisions**:
- **Trigger — decide before pulling this item.** The original item relied on a
  per-workspace auto-memory to make the agent run `start` and `done`
  unprompted. Memory is recalled as background context, not as an instruction;
  it is per machine; it is Claude-only. Since "the separate step does not
  happen" is the problem this skill exists for, the trigger cannot be
  deferred. The options, to be settled in this section before implementation:
  - (a) **user-invoked only** — the skill is a command and the item says so;
    honest, and the weakest at solving the stated problem;
  - (b) **a user-level hook** on the moments that call for `start`/`done` —
    most robust, most machinery, and Claude-only per ADR-0004;
  - (c) **`backlog-ops` suggests it** — its pull suggests `logbook start`,
    its close suggests `logbook done`, one line each, the same seam
    `commit-helper` → `design-record` already uses. This reverses the original
    item's "no change to `backlog-ops`" and is the current lean: it fires at
    exactly the right moments, ports with the skills, and costs two lines.
  Whichever lands, `SKILL.md` states how the skill is reached and the
  never-list gains nothing about memory.
- **No logbook-specific script.** The resolver and commit-and-push are shared
  and tested in [XAS-034](xas-034.md). Inserting a line under the right day
  and checking for an open `started` follow the logbook's `AGENTS.md` and are
  done by the agent in prose. This keeps "the rules live in the logbook"
  intact: a script would have to know the header and line format, which are
  exactly what the logbook defines. The cost is that insertion has no unit
  test; the end-to-end criterion covers the duplicate case instead.
- **Cites the two ADRs from [XAS-034](xas-034.md); writes none.** *Configured,
  not discovered* and *the store's `AGENTS.md` is the contract* are written
  there for the general case. If implementing this skill shows they were not
  general enough, amend them there.
- **Named `logbook`** because that names what it writes — not a method, not a
  particular repo. No alias.
- **Split from the learnings.** The original item bundled `start`/`done` with
  `capture`. They write to different stores under different rules, and only
  this half has a log format, a duplicate check and a trigger problem.
- **Minor version bump** of `xxthunder-dev-skills`: a new skill, no breaking
  change. If option (c) lands, the `backlog-ops` change is part of the same
  bump.

**Acceptance Criteria**:
- [ ] The trigger decision is recorded in Scope Decisions before implementation
      starts, and `SKILL.md` reflects it; if (c), `backlog-ops` pull and close
      each carry the one-line suggestion and its `SKILL.md` is listed in
      Component
- [ ] `SKILL.md` describes `start`, `note` and `done`, the resolution order,
      the `AGENTS.md` `Logbook` contract, the direction rule and the
      never-list; its trigger description names the three operations and the
      natural phrases
- [ ] The skill calls the shared resolver from [XAS-034](xas-034.md); no
      second resolver, no logbook-specific script
- [ ] Negative control: with neither variable set and outside a logbook, the
      skill stops with a message (the resolver's existing test covers the
      `LOGBOOK` prefix)
- [ ] `grep -ri` over the skill directory finds no path, remote or name of any
      specific logbook
- [ ] `docs/architecture.md` via `design-record`: the skill added to the
      components diagram and a *Chronicling a session* key flow, including
      the `done` → `capture` handoff
- [ ] `plugin.json` and `marketplace.json` bumped (minor); `README.md` and
      `CLAUDE.md` skill lists updated
- [ ] Verified end to end from a consuming repo that is not the logbook:
      `start` shows a prior line for the address, a second `start` on the
      same open address adds no line, `note` and `done` each land as one
      pushed commit, `done` leads to the capture question — and the consuming
      repo's working tree is untouched (`git status` clean there)

**Out of scope**:
- The logbook's own conventions — log location, day headers, line format,
  language. They belong to the logbook and are read from its `AGENTS.md`.
- The learnings — `capture`, `recall` — which are [XAS-034](xas-034.md).
- Any change to `retrospective`.
- Resolving a rebase conflict in the log automatically.
