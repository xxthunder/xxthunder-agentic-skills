# [XAS-097] ✅ DONE - The closed loop's GitHub checks read a re-run check by its newest attempt

**Status**: Done (2026-11-16)
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/scripts/host.py` (GitHub backend, `checks`), `tests/`
**Related**: [XAS-094](xas-094.md) (the rollup polling this item builds on), [XAS-090](xas-090.md) (waits for the pushed commit)

**Summary**:
As the author, I want `host.py checks` on GitHub to judge a re-run check by its newest attempt, so that a loop resumed after I re-ran a red CI ends on the re-run's verdict, not on the failed attempt.

**Description**:
Since XAS-094, `host.py checks` on GitHub reads the raw `statusCheckRollup` of `gh pr view`. `gh pr checks` does not read it raw: it removes duplicate checks and keeps the newest run per name, workflow and event. Whether a re-run leaves the failed attempt in the rollup is unverified; the final review of XAS-094 (2026-11-15) found no re-run in this repository's history to check against.

If the failed attempt stays in the rollup, the loop reads red forever after a re-run. That is the remedy the closed loop's stop *red CI after the fold* hands the author: re-run the CI, then continue the loop.

First check it: re-run one job of a pull request and read `gh pr view <n> --json statusCheckRollup`. If no duplicate appears, close this item with that finding. If one does, keep the newest entry per check, the way `gh pr checks` does.

**Finding** (2026-11-16):
The earlier attempt does not stay in the rollup. On pull request #42, run 43722108625 (attempt 1, both jobs green), the job `Tests (ubuntu-latest)` was re-run with `gh run rerun 43722108625 --job 132836130067` (gh 2.103.3). While attempt 2 ran, `gh pr view 42 --json statusCheckRollup` held one entry per check: `Tests (ubuntu-latest)` `IN_PROGRESS` under the new job ID 133416018775, `Tests (windows-latest)` with its old result under the new job ID 133416023602, and the two `Test Results` check runs of attempt 1 were gone. After attempt 2 finished, the rollup held the same six checks as before the re-run, each once: both `Tests` jobs and both `Test Results` runs of attempt 2, and the two `codecov` checks. GitHub's rollup shows only the newest attempt of a run, so `host.py checks` already judges a re-run check by its newest attempt.

The job re-run here had passed; a re-run of a failed job goes through the same attempt mechanism, but that exact case was not run. During a re-run the rollup can hold fewer checks than before, but one of them is still running, so `host.py checks` keeps waiting.
