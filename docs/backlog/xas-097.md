# [XAS-097] The closed loop's GitHub checks read a re-run check by its newest attempt

**Status**: Open
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/scripts/host.py` (GitHub backend, `checks`), `tests/`
**Related**: [XAS-094](xas-094.md) (the rollup polling this item builds on), [XAS-090](xas-090.md) (waits for the pushed commit)

**Summary**:
As the author, I want `host.py checks` on GitHub to judge a re-run check by its newest attempt, so that a loop resumed after I re-ran a red CI ends on the re-run's verdict, not on the failed attempt.

**Description**:
Since XAS-094, `host.py checks` on GitHub reads the raw `statusCheckRollup` of `gh pr view`. `gh pr checks` does not read it raw: it removes duplicate checks and keeps the newest run per name, workflow and event. Whether a re-run leaves the failed attempt in the rollup is unverified; the final review of XAS-094 (2026-11-15) found no re-run in this repository's history to check against.

If the failed attempt stays in the rollup, the loop reads red forever after a re-run. That is the remedy the closed loop's stop *red CI after the fold* hands the author: re-run the CI, then continue the loop.

First check it: re-run one job of a pull request and read `gh pr view <n> --json statusCheckRollup`. If no duplicate appears, close this item with that finding. If one does, keep the newest entry per check, the way `gh pr checks` does.

**Acceptance Criteria**:
- [ ] The rollup of a pull request with a re-run job is read with real `gh`, and the item records whether the failed attempt stays in it
- [ ] If it stays: `host.py checks` on GitHub judges each check by its newest attempt, with a test against a fake `gh`
- [ ] If it stays: the plugin's version is bumped in `plugin.json` and `marketplace.json`
