# [XAS-080] ✅ DONE - The closed loop runs its scripts where the repository's commands run

**Status**: Done (2026-11-19)
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/skills/closed-loop/SKILL.md`, `plugins/xxthunder-dev-skills/scripts/loop.py`
**Related**: [XAS-055](xas-055.md) (the closed loop), [XAS-070](xas-070.md), [XAS-095](xas-095.md) (pull request from the machine, folded in)

**Summary**:
As the author, I want the loop's scripts to work in a repository that is developed inside its
dev container, so that the loop records its state and guards its tests there without a
workaround.

**Description**:
The global rules create a worktree inside the dev container, so git records container paths
(`/workspaces/<workspace>/...`). On the host, that worktree is not a git repository. The skill
calls `loop.py` from the plugin cache on the host, so `state`, `guard`, `commit-impl`, `fixup`
and `fold` all fail there with "not a git repository".

On 2026-11-05/06, two loops for SPLed#132 ran in the DevPod workspace `spled`. The run copied
`loop.py` into the container's `/tmp` and called it with the container's `python3` over
`ssh spled.devpod`. That worked, because `loop.py` needs only the standard library, but nothing
in the skill says so, and the copy is lost when the container is rebuilt.

A push from the container works only through `devpod ssh <workspace> --command …`, which opens
DevPod's credential tunnel; a plain `ssh <workspace>.devpod` fails on the credential port.

**Acceptance Criteria**:
- [x] When the worktree's `.git` file names a git dir that does not exist on this machine,
      every `loop.py` subcommand that runs git maps it to the checkout's
      `.git/worktrees/<name>` and works, `fold` included
- [x] The loop's other git calls on the worktree (`merge-base`, `log`, `push`) run on the
      machine through `loop.py` as well; no git call of the loop needs the container
- [x] The skill says what runs in the container (the repository's commands and its gate) and
      what runs on the machine (`loop.py`, the push, `host.py`), from [XAS-095](xas-095.md)
- [x] A test shows `state`, `guard`, `commit-impl`, `fixup` and `fold` working on a worktree
      whose `.git` file names a path that does not exist, and runs in the Windows CI job
- [x] Resume finds the loop's worktree through a script, also when git made it in a
      container and the main checkout's link back to it names a container path
- [x] An eval case covers the skill's use of the mapping
- [x] The plugin's version is bumped in `plugin.json` and `marketplace.json`

**Scope Decisions**:
- **`loop.py` stays on the machine and maps the worktree's paths** (author, 2026-11-18). When
  the worktree's `.git` file names a git dir that does not exist on this machine, such as
  `/workspaces/<workspace>/.git/worktrees/<name>`, `loop.py` finds `.git/worktrees/<name>` of
  the checkout by walking up from the worktree, and runs git with `GIT_DIR` and
  `GIT_WORK_TREE` set to the two. Tried on 2026-11-18: git 2.54 in a container made a worktree
  at `/workspaces/repo`; host git 2.47 with both variables showed its status, committed, and
  gave the host's `--absolute-git-dir`; the container saw the commit, and the worktree's
  `.git` file stayed unchanged. `commondir` is already relative (`../..`). Rebase and push
  through the mapping are not tried yet.
- **No `loop.py` in the container** (author, 2026-11-18): the scripts run where the agent
  runs. The team develops in dev containers under WSL, and also on native Windows.
- **No relative worktree paths** (author, 2026-11-18): `git worktree add --relative-paths`
  (git 2.48+) sets `extensions.relativeWorktrees`, and older git then refuses the whole
  repository, main checkout included (tried with git 2.47.3). The company's git on Windows is
  2.45.x.
- **XAS-095 is folded in** (author, 2026-11-18): with the mapping, the push and `host.py` run
  on the machine anyway; the skill only has to say so.
- **Resume finds the worktree by its loop state** (author, 2026-11-18, from the final review
  of the loop run). Resume listed worktrees with `git worktree list`, but for a worktree made
  in a container the main checkout's link back to it (`.git/worktrees/<name>/gitdir`) names
  the container path: git on the machine lists that path as prunable, and the loop's state
  cannot be read there. A script finds the worktree from the loop states under
  `.git/worktrees/`, and the eval case writes a container path into that link too. This goes
  beyond the first criteria and is taken into this item, because a resumed loop in a dev
  container fails without it.
