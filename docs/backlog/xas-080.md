# [XAS-080] The closed loop runs its scripts where the repository's commands run

**Status**: Open
**Priority**: Medium
**Component**: `plugins/xxthunder-dev-skills/skills/closed-loop/SKILL.md`, `plugins/xxthunder-dev-skills/scripts/loop.py`
**Related**: [XAS-055](xas-055.md) (the closed loop), [XAS-070](xas-070.md)

**Summary**:
As the author, I want the loop's scripts to work in a repository that is developed inside its
dev container, so that the loop records its state and guards its tests there without a
workaround.

**Description**:
The global rules create a worktree inside the dev container, so git records container paths
(`/workspaces/<workspace>/...`). On the host, that worktree is not a git repository. The skill
calls `loop.py` from the plugin cache on the host, so `state`, `guard`, `commit-impl`, `fixup`
and `fold` all fail there with "not a git repository".

On 2026-11-05/06, two loops for SPLed#132 ran in the DevPod workspace `spled`. The run copied
`loop.py` into the container's `/tmp` and called it with the container's `python3` over
`ssh spled.devpod`. That worked, because `loop.py` needs only the standard library, but nothing
in the skill says so, and the copy is lost when the container is rebuilt.

A push from the container works only through `devpod ssh <workspace> --command …`, which opens
DevPod's credential tunnel; a plain `ssh <workspace>.devpod` fails on the credential port.

**Acceptance Criteria**:
- [ ] In a repository with a `.devcontainer/`, the skill runs every `loop.py` call inside the
      container, with the worktree's container path
- [ ] The skill pushes from the container through `devpod ssh <workspace> --command …`
- [ ] A test or eval case shows `loop.py state` and `guard` working on a worktree whose git
      paths exist only inside a container
